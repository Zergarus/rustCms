# Замер bxapi: CMS против Битрикса в Docker

Дата: 2026-11-13. Коммит CMS: `390b2cd` (код), результаты: `a5add2c`.
Хост: Apple M4 Pro, 14 ядер, macOS, Docker 29.1.3. Оба приложения — в Docker,
на одной машине, замеры по очереди.

## Что сравнивали

Пять POST-запросов, которые фронт TransOpt реально шлёт в `mediagroup.bxapi`:

| Ручка | Тело |
|---|---|
| Карточка товара | `/api/v1/iblock/catalog/element/38382` |
| Список товаров | `/api/v1/iblock/catalog/element/list`, `limit: 20` |
| Разделы каталога | `/api/v1/iblock/catalog/section/list`, `hasElements` |
| Поиск | `/api/v1/iblock/catalog/search`, `query: "U660"` |
| Схемы | `/api/v1/iblock/schemes/element/list`, `imageResize: [300,800]` |

Тела — `bench/payloads/*.json`, один и тот же генератор
`bench/load.py` для обеих систем.

## Стенд

- **CMS:** образ из `Dockerfile`, контейнер в сети Bitrix, PostgreSQL 17.
  `CSRF_ENFORCE=false`, `RATE_LIMIT_PER_MIN=0` — только на время замера.
  PostgreSQL — рабочий `transoptrusttest-postgres-1`, доступен через
  `host.docker.internal`; это добавляет NAT-плечо к каждому запросу CMS.
- **Битрикс:** MariaDB — общий `bitrix-common-db` на bench-сети; база общая с
  другими локальными сайтами, поэтому во время прогона её нельзя нагружать.
- **Битрикс:** отдельный `bench-php-fpm` из того же php-fpm-образа, что и
  рабочий стенд, но с Xdebug off, OPcache+JIT on и пулом
  `pm=static; pm.max_children=32`; отдельный `bench-bitrix-nginx`. Рабочие
  `transopt-local-*` контейнеры не менялись.
- Оба приложения за nginx, HTTP, `Host: transopt.local`; Битриксу добавлен
  `X-Forwarded-Proto: https`, иначе его nginx отдаёт 308.
- Лимиты приложений: `--cpus=4 --memory=2g`; nginx без лимитов.

### Данные

Снимок — `bench/snapshot.json`. Совпали:

- товар 38382: одинаковый id и название;
- поиск `U660`: по 10 товаров и 1 марка;
- counts по парам коллекций: `catalog`/`task` 5149, `models`/`auto_variants`
  6500, `auto` 2053, `marks` 1176, `locations` 1355, `schemes` 421,
  `news` 25, `info` 143.

Дамп БД в git не коммитился: это живая dev-база. Оба стенда гонялись подряд,
только чтение. Полная воспроизводимость через неделю не гарантируется, если
данные изменятся.

## Методика

- **Latency:** c=1, 200 последовательных запросов после прогрева 30. p50/p95/p99.
- **Throughput:** c=16, 10 секунд, keep-alive. Rps — это **throughput при 16
  клиентах**, а не предельная пропускная способность: ни генератор, ни 4-CPU
  лимит CMS отдельно не характеризованы.
- Два полных перемежающихся раунда (CMS/Битрикс менялись местами), в таблицах —
  медиана; в скобках — min–max по раундам. **Важно:** второй раунд собирался,
  когда хост несколько раз уходил в паузы; все значения Битрикса во втором
  раунде хуже первого. Поэтому «×» — медиана отношений по раундам, а в скобках
  — разброс; это не чистый «потолок» отношения. Третий раунд начат, но
  исключён. Это ограничение, а не «три прогона».
- Генератор запускался на хосте через опубликованные порты (не в контейнере):
  фиксированная NAT-надбавка входит в обе стороны, но для 5–8 мс CMS она
  относительно больше. Ошибок и не-200 в учтённых прогонах нет.
- Память: `docker stats --no-stream` на простаивающих контейнерах.

## Как читать

- При c=1 CMS отвечает в **4,7–8,9 раз** быстрее на обычных ручках и в **43
  раза** на «Схемах» (медиана; 22–65× по раундам) — там Битрикс отдаёт
  185–186 КБ JSON и заметно деградирует.
- При c=16 разница в throughput — **8–97 раз по медиане** (6–133× по раундам).
  Это не «предел CMS»: и генератор, и 4-CPU-лимит CMS не характеризованы
  отдельно; цифра показывает, что CMS держит как минимум столько при той же
  конкуренции.
- Разброс Битрикса большой (например, схемы 1,4–6,7 rps при c=1): сказываются
  прогрев, паузы хоста и общая MariaDB с другими локальными сайтами. Медиана
  двух раундов — не SLA.

## Ограничения

- Локальный dev-стенд Битрикса, не production-тюнинг; PHP-FPM и MariaDB —
  другие, чем PostgreSQL у CMS.
- Docker Desktop на macOS искажает абсолютные цифры; относительное сравнение
  на одном хосте полезно, но это не бенчмарк «язык против языка».
- TLS не измерялся: оба приложения за HTTP-nginx, Битриксу добавлен
  `X-Forwarded-Proto`.
- Ответы не байт-в-байт: CMS 2,5 / 13,8 / 42,6 / 3,1 / 195 КБ против
  Битрикса 4,4 / 19,4 / 68,5 / 4,7 / 186 КБ на соответствующих ручках. Разница
  сериализации влияет на схемы особенно сильно.
- Учтено два полных раунда, третий исключён из-за пауз хоста; дамп данных не
  заморожен.
- Только чтение. Заказы, оплата, регистрация и запись не измерялись.

## Воспроизведение

```bash
bash bench/setup.sh --check          # отдельный Bitrix + CMS за nginx
bash bench/snapshot.sh               # проверка данных и counts
BENCH_ROUNDS=2 bash bench/run.sh     # 5 ручек × 2 системы × 2 режима
python3 bench/summarize.py bench/results --json-out bench/summary.json
```

Исходный прогон запускался как `BENCH_ROUNDS=3 bash bench/run.sh`; два раунда
завершились, третий исключён. `run.sh` по умолчанию теперь делает 2 раунда —
столько же, сколько в отчёте.

Сырые результаты — `bench/results/*.json`; снимок —
[`bench/snapshot.json`](../bench/snapshot.json); старый замер —
[benchmark-bitrix-vs-rust.md](benchmark-bitrix-vs-rust.md).
