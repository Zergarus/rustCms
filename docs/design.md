# Дизайн админки

Направление: **Utility & Function + Precision** — спокойные холодные нейтрали,
один акцент, плотная информация, бордеры вместо теней. Шрифт Inter, базовая
сетка 4px, числа — табличные, деньги и количества — фильтры `money`/`num`.

## Аудит (2026-11-10, скриншоты 1440×900)

Сняты: рабочий стол, коллекции, заказы, заказ, карточка записи, настройки,
письма, очередь. Найдено:

- в карточке заказа суммы в правой колонке — сырые (`6897.2`) и без
  выравнивания, значения на узкой колонке наезжали на подписи;
- в таблице состава числа не форматировались и переносились на две строки;
- действия карточки заказа (статус, оплата, отмена) висели в разных местах:
  кнопки то слева, то справа, между ними пустота;
- вкладки переносились на вторую строку и не выглядели как один контрол;
- форма настроек растягивала короткие поля на 1110px;
- рабочий стол: три огромные карточки с числами и пустота ниже, никаких
  действий и контекста;
- подписи в боковом меню и заголовки таблиц — без единой типографики,
  числа без разрядности.

## Что сделано

- `static/admin/design.css` — слой поверх `admin.css`: токены отступов,
  радиусов, размеров текста; кнопки одной высоты (32px); поля 34px с фокус-
  кольцом; плотные таблицы с липкой шапкой, hover и выравниванием чисел;
  сегментированные вкладки в одну строку; карточки с бордером; боковое меню
  с заголовками групп; статистика рабочего стола.
- `money`/`num` в шаблонах: `6 897,20`, `23 119` — единый формат в карточке
  заказа, письмах-предпросмотрах, составе и на рабочем столе.
- Карточка заказа: строки формы «подпись — поле», действия — отдельной
  строкой справа; правые свойства — стеком, числа в моно.
- Рабочий стол: блок «Последние заказы» (5 штук, только при праве на заказы)
  рядом со статистикой и API.

## Итерация 2 (по замечаниям к тёмной теме)

- **Вкладки** больше не «плашки в контейнере»: плоские вкладки с подчёркиванием
  активной, без фона и без переноса — помещаются в одну строку и в карточке
  заказа, и в карточке записи.
- **Блок статуса заказа** стал компактным: три строки «подпись — поле»,
  действия стоят в той же строке справа, формы разделены линией. Кнопки
  уменьшены до 30px, радиус 6px — перестали выглядеть «игрушечными».
- **Список коллекции**: панель видов и фильтры/колонки съехались в одну
  строку с общим нижним бордером; строки таблицы плотнее, дерево разделов
  липкое.
- **Настройки**: две карточки-секции («Сайт», «Почта») с сеткой полей 2×N;
  SMTP больше не висит «главным» блоком в общих настройках.
- **Модули**: список карточек, по одной на модуль; внутри — название, статус,
  короткое описание и строка «Включает: …», справа переключатель. Одна кнопка
  «Сохранить» под списком; новый модуль — ещё одна карточка, без отдельных
  блоков-дублей.
- Тёмная тема проверена скриншотами (ранее смотрели только светлую).

## Итерация 3 (системные правки по полному аудиту)

- Полоса открытых вкладок: ширина вкладки ≤200px, название с многоточием,

- Мобильный (≤900px): таблицы списка с минимальной шириной 720px и подсказкой

## Итерация 4 (батч 2 аудита)

- Карточка заказа: блок «Управление заказом», опасная зона отделена линией,
  отмена раскрывается через «Отменить заказ» → причина → подтверждение
  (постоянное поле причины убрано из основного сценария).
- Единые варианты меток: `badge ok / warn / danger / accent`; в сводке заказа
  статус, оплата, отгрузка и доставка показаны метками с текстом.
- Модель ширины форм: `.form-narrow` (820px) для правил скидок и обмена с 1С.

### Батч 2, продолжение

- Чекбоксы и радио в подписях получили жёсткий размер 16×16 и `flex: 0 0 16px`:
  раньше глобальное `input { width: 100% }` растягивало сам чекбокс, из-за чего
  метка уезжала к правому краю (видно было в «Обмене с 1С»).
- Формы правил скидок и обмена ограничены `.form-narrow` (820px).

### Батч 2: карточка товара, вкладка «Каталог»

Пустое место слева было следствием двухколоночной сетки: справа список
складов выше цен в 3–4 раза, сетка растягивала колонки по высоте. Перестроил
вкладку в стопку секций: «Торговый каталог» → «Цены» → «Остатки». Остатки —
таблица «Склад / Остаток» вместо длинного столбца полей; у склада виден `#id`,
потому что в данных есть магазины-дубли с одинаковыми названиями.

### Батч 3: метки в списках

Движок списков научился выводить значение меткой: у колонки появился
`badge: bool`, ячейка получает `flag = "badge"`, шаблон рисует `.badge`.
Первым подключён статус заказа — в таблице заказов он больше не сливается с
текстом.

### Батч 3: SEO как вкладка

SEO переехал из отдельной страницы в вкладку карточки записи: поля Title,
Description, H1, Canonical и индексация сохраняются общей кнопкой «Сохранить»
вместе с записью (SEO пишется после сохранения, ошибка SEO не откатывает
запись). Отдельная страница осталась для просмотра наследованных значений.

### Батч 3: даты и таблицы

- «Дата публикации» в карточке — текстовое поле `ДД.ММ.ГГГГ ЧЧ:ММ` (UTC) вместо
  системного `datetime-local`: формат больше не зависит от локали браузера.
  Сервер принимает `ДД.ММ.ГГГГ ЧЧ:ММ`, `ДД.ММ.ГГГГ` и старый ISO.
- Фиксированные колонки (`table-fixed` + `colgroup`) для групп и коллекций:
  длинные названия обрезаются, действия не уезжают.
- Кнопка сохранения на отдельной странице SEO выровнена как в остальных формах.

### Батч 3: даты в скидках и дубли складов

- Все `datetime-local` в правилах скидок, накопительных скидках и купонах
  заменены текстовыми полями `ДД.ММ.ГГГГ ЧЧ:ММ`; парсер принимает RU, ISO и
  дату без времени.
- В локальной базе слиты склады-дубли (`scripts/merge_duplicate_stores.sql`):
  остатки, штрихкоды, партии и привязки доставки перенесены на склад с
  минимальным id; было 8 складов, стало 5. Скрипт идемпотентен.

## Инструменты супер-администратора (2026-11-11)

Меню «Система» → «Инструменты»: SQL-запрос, Таблицы БД, Rust-скрипты.
Пункт виден только суперу (`users.is_admin`) и только при `ADMIN_TOOLS_ENABLED=1`.
Обычный администратор, даже с правом `settings.manage`, получает 403; при
выключенном флаге страницы отдают 404, а пункта нет ни в меню, ни в палитре
действий. Все страницы работают в обычной оболочке админки, с CSRF, сессией и
записью в `audit_log`. Данные в инструментах **не маскируются**.

### SQL-запрос (`/admin/tools/sql`)

- Произвольный SQL в текстовой области. Без галочки «Запрос может изменить
  данные» запрос идёт в транзакции `READ ONLY` и откатывается; с галочкой —
  в обычной транзакции с `COMMIT`.
- За один раз выполняется один statement: extended protocol не принимает
  несколько команд, одиночные `SET/RESET/CALL/BEGIN/COMMIT/ROLLBACK` запрещены,
  чтобы нельзя было выйти из `READ ONLY` или сбросить таймаут.
- `statement_timeout = 15s` на транзакцию. Вывод — не больше 200 строк и 256 КБ;
  при обрезке страница это показывает. Ошибка БД выводится в alert, страница
  остаётся рабочей.
- В журнал (`action=sql`, `entity=tools`) попадают первые 500 символов запроса,
  статус и число строк; полного текста и истории запросов нет.
- В таблице результата — `NULL`, bool, числа, даты, json, uuid, bytea (hex,
  обрезано); остальные типы — строкой.

### Таблицы БД (`/admin/tools/db`)

- Список: пользовательские схемы (кроме `pg_catalog`, `information_schema`,
  `pg_toast`, `pg_temp*`), таблицы, партиционированные таблицы, представления и
  matview. Для каждой — оценка строк (`pg_class.reltuples`), размер, число
  колонок и признак PK.
- Страница таблицы: структура (имя, тип, null, default, PK, generated),
  данные по 50 строк, сортировка по клику на колонку, пейджер. Точный
  `count(*)` выполняется с таймаутом 5 с; если не успел — показывается оценка
  без числа страниц. Отдельного показа индексов и ограничений нет.
- Правка строк доступна только таблицам (`r`/`p`) с первичным ключом; у
  представлений и таблиц без PK страница только для чтения. Значения уходят
  bind-параметрами, идентификаторы берутся из каталога и экранируются;
  generated-колонки в формы не попадают.
- DDL: создать таблицу (схема, имя, до 5 колонок в форме: имя, тип, null,
  default, PK), удалить таблицу (подтверждение вводом имени), добавить и
  удалить колонку. Имена — `^[a-z_][a-z0-9_]*$` и не длиннее 63 символов, типы —
  из списка `text, varchar(n), integer, bigint, smallint, numeric(p,s), boolean,
  date, timestamp, timestamptz, uuid, jsonb, bytea`, default — только
  безопасный литерал. Остальные типы в существующих таблицах показываются и
  правятся как текст, если Postgres принимает ввод.
- Таймауты: 15 с на запись строки и на DDL. Журнал: `db-row-insert/update/delete`
  с таблицей и PK, `db-table-create/drop`, `db-column-add/drop`. Истории
  изменений данных и структуры, кроме журнала, нет.

### Rust-скрипты (`/admin/tools/rust`)

- Скрипты хранятся в `admin_rust_scripts` (имя уникально, до 100 символов).
  Редактор: имя + textarea кода, «Сохранить», «Запустить», «Удалить».
- Код — тело внутри `async fn main`, где уже есть `pool: sqlx::PgPool` и
  зависимости `sqlx 0.9` (postgres, chrono, json, uuid), `serde_json`, `chrono`,
  `uuid`, `tokio`. Запускается **сохранённый** код; несохранённые правки формы
  не выполняются.
- Запуск собирает временный crate в `std::env::temp_dir()/cms-rust/<uuid>`
  (`cargo build --quiet`) и запускает бинарник. Общий `CARGO_TARGET_DIR`
  (`RUST_SCRIPT_TARGET_DIR`, по умолчанию `target/rust-scripts`) кэширует
  зависимости между запусками.
- Таймауты: сборка 180 с, выполнение 30 с (меняются `RUST_SCRIPT_BUILD_TIMEOUT`
  и `RUST_SCRIPT_RUN_TIMEOUT`). По истечении процесс убивается. Вывод — до 64 КБ
  **на каждый поток** (stdout и stderr отдельно), при обрезке есть пометка.
- Дочернему процессу передаются только `DATABASE_URL`, `PATH`, `HOME`,
  `CARGO_HOME`, `RUSTUP_HOME`; секреты приложения (`SESSION_SECRET`, SMTP) не
  передаются. Одновременно выполняется один скрипт — второй запрос получает
  сообщение «выполняется другой скрипт».
- История — последние 50 запусков на скрипт (`admin_rust_runs`), в списке
  показывается превью вывода до 200 символов. Журнал: `rust-run` с именем,
  статусом и длительностью.
- Страница постоянно предупреждает: это произвольный код с правами процесса CMS
  и доступом к `DATABASE_URL`, песочницы нет.
- Нужен Rust toolchain: `cargo` и `rustc` в `PATH` (rustup). Если их нет,
  запуск возвращает понятную ошибку с инструкцией по установке. Первая сборка
  долгая: нужны сеть или прогретый кэш cargo.

### Конфигурация

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ADMIN_TOOLS_ENABLED` | `1` | `0` — страницы 404 и пункта меню нет |
| `RUST_SCRIPT_TARGET_DIR` | `target/rust-scripts` | общий каталог сборки, относительно каталога проекта или абсолютный |
| `RUST_SCRIPT_BUILD_TIMEOUT` | `180` | таймаут сборки, секунды |
| `RUST_SCRIPT_RUN_TIMEOUT` | `30` | таймаут выполнения, секунды |

Переменные продублированы в `.env.example`.

### Опасности и ограничения

- Произвольный код и DDL необратимы; защита — только супер-права,
  подтверждения, таймауты и журнал.
- Песочницы нет: скрипт видит `DATABASE_URL`, файловую систему и сеть процесса
  CMS; маскирования данных нет — видны хеши паролей, сессии и ключи API.
- Тяжёлые запросы, `count(*)` и DDL нагружают БД; отсюда таймауты.
- Нет истории SQL-запросов, истории правок строк/структуры (только журнал) и
  отката изменений.
- Убийство по таймауту достаётся только прямому дочернему процессу: внуки
  (`rustc`, линковщик) могут дожить до конца сборки.
- Временные каталоги `cms-rust/<uuid>` удаляются после запуска; при падении
  процесса могут остаться. Общий target-dir растёт с числом зависимостей.

Скриншоты: `docs/design/tools-sql.png`, `tools-db.png`, `tools-rust.png`.
