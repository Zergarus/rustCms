# Торговые предложения (SKU) — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Торговые предложения как в Битриксе «Бизнес»: коллекция предложений, связь `CML2_LINK` через колонку `product_id`, тип и доступность товара по триггеру, вкладка и генератор в админке, `catalogType` / цена «от» / фильтр `offers` в bxapi, свойства позиции в корзине и заказе, импорт из Битрикса.

**Architecture:** Предложение — обычная запись коллекции предложений; связь с товаром — колонка `collection_items.product_id`. Для bxapi, админки и импорта она выглядит как поле-привязка `CML2_LINK`: при чтении значение подмешивается в `field_values` одним SQL-выражением, при записи вынимается из них. Тип (1/3/4/6) и доступность родителя пересчитывают триггеры БД.

**Tech Stack:** Rust 2024, Axum 0.8, SQLx 0.9 (PostgreSQL 17), MiniJinja, uuid.

**Spec:** `docs/superpowers/specs/2026-10-09-sku-design.md`. План выполняется после `docs/superpowers/plans/2026-10-09-collections-rename.md` и использует его имена (`Collection`, `Item`, `Field`, `FieldOption`, `collection_items.field_values`, `catalog_products.item_id`, `test_support::{test_state, admin_cookie, content_fixture}`, `smoke_tests::{get, post_form}`).

## Global Constraints

- Коды типа товара — как в Битриксе: 1 простой, 3 с предложениями, 4 предложение, 6 с предложениями без предложений.
- Системное поле связи: код `CML2_LINK`, вид `element`, привязка к коллекции товаров; новая коллекция предложений — код `<код>_offers`, название «<название> — предложения», каталог включён.
- Тексты: «Торговые предложения», «Добавить предложение», «Сгенерировать», «Цены и остатки задаются у предложений», «Показывать в корзине», «Поле выбора предложения», «Создано N, пропущено M (уже есть)», ошибка товара в корзине — `product_not_found` «Товар не найден».
- Генератор: не больше 100 сочетаний за запуск; шаблон по умолчанию `#PRODUCT_NAME# (#CODE1#, #CODE2#)` из кодов полей выбора; `xml_id` нового предложения — UUID v4.
- Служебные свойства позиции: `PRODUCT.XML_ID`, `CATALOG.XML_ID`; в админке и письме не показываются.
- bxapi: пути и поля контракта не меняются; расширения — только `catalogType`, `catalogPrice.fromOffers`, ключ фильтра `offers`. Наш API: пути и ключи не меняются, добавляются `product_id` и `catalog.type`.
- Значения цен, остатков, типов, свойств — пакетными запросами на страницу, не на запись.
- Тесты: `rtk proxy cargo test` (лог в файл, читать хвост); `cargo fmt`; `cargo clippy --all-targets` без предупреждений; то же без `projects/`.
- Коммиты на русском, без упоминаний Claude/ИИ. В локальный Битрикс запросы с побочными эффектами не отправлять. Демо-данные и тестовые заказы не удалять.

## Review Focus

1. Предложение неактивного товара кладут в корзину. Ожидается `product_not_found`, как у неактивного товара (в Битриксе товар-родитель снимает с продажи свои предложения). Тест `offer_of_inactive_product_not_purchasable`, Задача 6.
2. Предложение сохраняют в админке без товара или с товаром из чужой коллекции. Ожидается ошибка формы «Укажите товар из коллекции <название>», запись не создаётся. Тест `offer_requires_product`, Задача 3.
3. Связь снимают или коллекцию предложений удаляют, когда в ней есть записи. Ожидается отказ с сообщением «Сначала удалите предложения (N)». Тест `unlink_refused_with_offers`, Задача 3.
4. У товара все предложения недоступны. Ожидается: цена «от» — самое дешёвое активное предложение (цена видна, `available` товара false); нет активных — `catalogPrice: []`, как у товара без цен. Тест `price_from_falls_back_to_active`, Задача 5.
5. Генератор при повторном запуске с теми же значениями, но в другом порядке галочек. Ожидается: все сочетания пропущены как существующие (сравнение без учёта порядка полей). Тест `generator_skips_existing_any_order`, Задача 4.

Решение плана, отличное от спецификации: у товара типа 6 `catalogPrice` — `[]` (как у любого товара без цен в текущем bxapi), а не `null`.

### Task 5: bxapi — catalogType, цена «от», фильтр offers

**Files:**
- Modify: `src/bxapi/serialize.rs` (`Loaded`: `types`, `from_offers`), `src/bxapi/filter.rs` (`push_leaf`: ключ `offers`), `src/bxapi/registry.rs` (в `Schema` — схема коллекции предложений: `offers: Option<i64>`)
- Test: `src/bxapi/serialize.rs`, `src/bxapi/filter.rs`, `src/smoke_tests.rs`

**Interfaces:**
- `catalogType` — число из `catalog_products.type` (нет строки — 1); `null` у коллекции без каталога.
- Цена «от»: для строк типа 3 — один запрос на страницу: активные предложения, их `available`/остатки и цены; выбирается предложение с минимальной основной ценой (`catalog::main_price`) среди доступных, нет доступных — среди активных; `catalogPrice` = цены этого предложения + `"fromOffers": true`; `stocks` — суммы по складам по всем активным предложениям. Тип 6 и нет активных — `catalogPrice: []`, `stocks: []`.
- `pub fn pick_from_offer(offers: &[(i64 /*offer*/, bool /*available*/, Vec<Price>)]) -> Option<i64>` — чистая функция выбора.
- Фильтр: ключ `offers` (без операторов) у коллекции, у которой есть коллекция предложений → `EXISTS (SELECT 1 FROM collection_items o<N> WHERE o<N>.product_id = <alias>.id AND o<N>.collection_id = $offers AND <вложенный фильтр>)`, контекст `nested` (глубина +1, `MAX_DEPTH`); внутри `offers` ключ `offers` → `unknown_field`; у коллекции без предложений → `unknown_field("offers")`. Внутри `offers` доступны только ключи, которые фильтр уже умеет для любой коллекции; новых каталожных ключей не добавляется.
