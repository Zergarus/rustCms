# Инструменты супер-администратора: SQL, таблицы БД, Rust-скрипты

Дата: 2026-11-11. Статус: предложено, ждёт утверждения.

## Зачем

Паритет с административными инструментами Bitrix: на production нужны
постоянные страницы для SQL-запросов, просмотра и правки таблиц БД и запуска
скриптов на Rust. Доступ — только доверенным супер-администраторам.

## Цели

- SQL-консоль: выполнить любой запрос и увидеть результат/ошибку.
- Обозреватель таблиц: все пользовательские схемы, структура, данные,
  редактирование строк, создание/удаление таблиц и колонок.
- Rust-скрипты: произвольный код из браузера, компиляция и запуск на сервере.
- Всё пишется в журнал действий; обычные администраторы и группы доступа
  инструменты не видят.

## Не-цели

- Песочница для Rust-кода и защита от вредоносного супер-админа. Код
  выполняется с правами процесса CMS и доступом к `DATABASE_URL`.
- Замена миграций, резервного копирования и мониторинга.
- Маскирование чувствительных данных: по требованию таблицы показываются как
  есть, включая хеши паролей, сессии и ключи API.

## Анти-цели

- Инструменты не должны быть доступны не-суперам, даже с правом
  `settings.manage`.
- Запросы и скрипты не должны блокировать пул соединений бесконечно.
- Ошибка инструмента не должна ронять админку или портить данные молча.

## Выбранный подход

Рассматривались:

- **A. Read-only диагностика** (таблицы и `SELECT` без изменений) — безопасно,
  но не закрывает запрос.
- **B. Полный аналог Bitrix** — любой SQL, полноценный DB-клиент, произвольный
  Rust. Максимальная свобода и риск; выбран пользователем.
- **C. Реестр задеплоенных Rust-операций** — безопаснее, но это не Bitrix.

Выбран **B**. Осознанные последствия: production-админка даёт выполнение кода
и прямые изменения БД; защита строится на супер-правах, подтверждениях,
таймаутах и журнале, а не на песочнице.

## Доступ

- Все страницы требуют `Access::require_super()` (`users.is_admin`).
- Новое право `tools.manage` не вводится: его нельзя выдать группе.
- Пункт меню «Инструменты» виден только суперу и только при включённом
  `ADMIN_TOOLS_ENABLED`.
- `ADMIN_TOOLS_ENABLED=0` полностью выключает страницы (404) и пункт меню.
  По умолчанию `1`, чтобы инструмент работал на production без правки кода.
- CSRF, сессия, same-origin guard и обычная оболочка админки действуют.

## Маршруты и меню

В группе «Система» появляется пункт «Инструменты» → страницы:

- `/admin/tools/sql` — SQL-консоль.
- `/admin/tools/db` — список таблиц.
- `/admin/tools/db/{schema}/{table}` — таблица: структура, данные, правка.
- `/admin/tools/rust` — список/редактор Rust-скриптов.

Шаблоны: `templates/admin/tools/sql.html`, `db_list.html`, `db_table.html`,
`rust.html`. Вкладки открываются как обычные страницы (`tab_key`).

## SQL-консоль

- Одна текстовая область, кнопка «Выполнить», чекбокс подтверждения
  «Запрос может изменить данные».
- Выполняется как есть, без неявной транзакции. Postgres сам решает, сколько
  statement'ов в запросе; результат — набор строк последнего SELECT либо
  «выполнено, затронуто N строк».
- `statement_timeout = 15s` на сессию; вывод — не более 200 строк и 256 КБ.
- Ошибка БД показывается в alert с текстом; страница остаётся рабочей.
- Аудит: `action=sql`, `entity=tools`, summary = первые 500 символов запроса +
  статус/число строк. Полный текст не хранится.
- Форматирование значений: null, bool, числа, даты/timestamptz, json, uuid,
  bytea (hex, обрезано), остальное — `to_string`.

## Обозреватель таблиц

Список:

- Схемы, кроме `pg_catalog`, `information_schema`, `pg_toast`; таблицы и
  представления с оценкой строк, размером, числом колонок и признаком PK.

Таблица:

- Структура: колонки (имя, тип, null, default, PK), индексы, ограничения.
- Данные: страница по 50 строк, сортировка по клику на колонку, переход по
  страницам, точный `count(*)` с таймаутом.
- Редактирование: только таблицы с одно- или составным PK. Форма строки
  (input по типу), «Сохранить», «Удалить» с подтверждением; «Добавить строку».
  Значения подставляются bind-параметрами, идентификаторы — только после
  проверки по списку таблиц/колонок и экранирования кавычками.
- DDL: создать таблицу (имя + колонки: имя, тип, null, default, PK), удалить
  таблицу, добавить/удалить колонку. Удаление — подтверждение вводом имени.
- Ограничения v1: типы `text, varchar, integer, bigint, numeric, boolean, date,
  timestamp, timestamptz, uuid, jsonb`; остальные показываются, но правятся
  как текст только если Postgres принимает ввод. Колонки с default можно
  оставить пустыми при вставке.
- Аудит: `db-row-*`, `db-table-*`, `db-column-*` с именем таблицы и PK.

## Rust-скрипты

Хранение:

- `admin_rust_scripts`: id, name, code, created_by, updated_by, created_at,
  updated_at. Имя уникально.
- `admin_rust_runs`: id, script_id, user_id, user_login, started_at,
  duration_ms, ok, output, error. Хранится последние 50 запусков на скрипт
  (старые удаляются при вставке).
- Редактор: имя + textarea кода, «Сохранить», «Запустить». Запуск сохраняет
  текущий код и выполняет его.

Контракт кода:

- Пользователь пишет тело внутри `async fn main`, где уже доступны
  `pool: sqlx::PgPool` и стандартные зависимости.
- Генерируемый файл:

```rust
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let url = std::env::var("DATABASE_URL")?;
    let pool = sqlx::PgPool::connect(&url).await?;
    // --- код пользователя ---
    Ok(())
}
```

- Разрешённые зависимости: `sqlx` (postgres, chrono, json, uuid), `serde_json`,
  `chrono`, `uuid`, `tokio`. Версии фиксируются в генерируемом `Cargo.toml` и
  совпадают с проектом.
- Первый запуск создаёт временный crate, собирает его `cargo build` и запускает
  бинарник; общий `CARGO_TARGET_DIR` кэширует зависимости между запусками.
- Таймауты: сборка 180 с, выполнение 30 с; по истечении процесс убивается.
  Вывод — до 64 КБ, обрезается с пометкой.
- Переменные окружения: `DATABASE_URL`, `PATH`, `HOME`, `CARGO_HOME`,
  `RUSTUP_HOME`; остальные не передаются.
- Одновременно выполняется один скрипт (процессный mutex). Вход в очередь
  показывает «выполняется другой скрипт».
- Если `cargo`/`rustc` не найдены, страница показывает инструкцию, запуск
  возвращает понятную ошибку.
- Безопасность: это выполнение произвольного кода. В интерфейсе постоянное
  предупреждение; аудит `rust-run` с именем, статусом и длительностью.

## Конфигурация

- `ADMIN_TOOLS_ENABLED` — `1`/`0`, по умолчанию `1`.
- `RUST_SCRIPT_TARGET_DIR` — общий каталог сборки, по умолчанию
  `target/rust-scripts`.
- `RUST_SCRIPT_BUILD_TIMEOUT` / `RUST_SCRIPT_RUN_TIMEOUT` — секунды,
  по умолчанию 180/30.

## Схема БД

Миграция `0042_admin_tools.sql`: таблицы `admin_rust_scripts` и
`admin_rust_runs` с индексами по имени и script_id/created_at. SQL-история и
история правок таблиц не создаются — только `audit_log`.

## Тесты

- Доступ: не-супер получает 403 на всех четырёх маршрутах; супер видит меню.
- SQL: SELECT возвращает строки; ошибка показывается; запись аудита создаётся.
- Таблицы: список содержит тестовую таблицу; чтение данных; вставка, правка,
  удаление строки; create/drop таблицы; отклонение имени с кавычками.
- Rust: валидация имени, сохранение, запуск при наличии toolchain (тест
  помечен `#[ignore]`, включается переменной окружения), аудит.
- Миграция поднимается на чистой БД.

## Этапы

1. Доступ, меню, выключатель, миграция, аудит-каркас.
2. SQL-консоль.
3. Обозреватель таблиц: список, структура, данные.
4. Правка строк и DDL.
5. Rust-скрипты: хранение, редактор, запуск, таймауты.
6. Проверки на production-подобной БД и документация.

## Риски

- Произвольный код и DDL необратимы; защита — только права, подтверждения,
  таймауты и журнал.
- Сборка Rust требует toolchain и сети/кэша зависимостей; первый запуск долгий.
- Тяжёлые `SELECT`/DDL могут нагружать БД; таймаут обязателен.
- Инструменты видят все данные, включая секреты; это принятое требование.
