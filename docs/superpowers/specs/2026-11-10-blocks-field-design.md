# Поле коллекции «Блоки» (аналог `sprint.editor`)

## Зачем

Богатый контент сейчас хранится как HTML в поле `text`: вёрстка страниц
разъезжается, редакторы ломают разметку, а фронтенду нечего структурировать.
`sprint.editor` в Битриксе решает это блоками: контент — это список
типизированных блоков, а не одна строка HTML. Нужен такой же тип **поля
коллекции** `blocks`.

## Цели

- Поле коллекции `blocks`: массив блоков в `field_values`, без отдельной таблицы.
- Фронт получает **JSON-массив блоков**, а не HTML: блок — это `type` плюс поля
  этого блока латиницей (`text`, `heading`, `image`, …). Фронт рендерит сам.
- Редактор в админке: добавить/переставить (drag&drop)/дублировать/удалить блок,
  заполнить его поля, загрузить картинку.
- Массовые операции, версии, импорт/экспорт и `search_vector` работают как есть.

## Не-цели

- Серверный рендер блоков в HTML (фронт рендерит JSON).
- Блоки «видео», «файл», «кнопка» — второй заход.
- Импорт JSON `sprint.editor` — отдельная задача.
- Библиотека блоков и переиспользование между записями.

## Подходы

- **A. JSON в `field_values` (выбран).** Плюс: без миграции данных, версии и
  экспорт уже работают, минимум кода. Минус: блоки не запрашиваются SQL’ем —
  для контента не нужно.
- **B. Таблица `item_blocks`** (строка на блок). Плюс: блоки — данные. Минус:
  версии перестают быть снимком строки, сериализация и миграция — заметно
  больше работы без пользы для v1.
- **C. Обычный WYSIWYG-HTML.** Отвергнут: не даёт структуры, ради которой
  делается поле.

## Формат

Значение поля — массив объектов; у каждого есть `type`, остальные ключи —
латиницей и относятся к типу. Для блока с одним содержимым ключ называется по
типу блока.

```json
[
  { "type": "heading", "heading": "Наши преимущества", "level": 2 },
  { "type": "text", "text": "Первая строка.\n\nВторой абзац." },
  { "type": "image", "image": "/upload/abc.jpg", "alt": "Склад", "caption": "Склад в Москве" },
  { "type": "gallery", "images": [ { "image": "/upload/a.jpg", "alt": "" } ] },
  { "type": "quote", "quote": "Быстро и точно", "author": "Иван" },
  { "type": "table", "rows": [ ["Параметр", "Значение"], ["Объём", "3 л"] ] },
  { "type": "divider" },
  { "type": "html", "html": "<div class=\"note\">Заметка</div>" }
]
```

Правила:

- `heading`: `heading` (строка), `level` — 2, 3 или 4 (по умолчанию 2).
- `text`: `text` — обычный текст, абзацы разделяются `\n\n`; без HTML.
- `image`: `image` — путь `/upload/...`, `alt`, `caption`, `link` (необязательные).
- `gallery`: `images` — массив `{ image, alt, caption }`.
- `quote`: `quote`, `author`.
- `table`: `rows` — массив массивов строк; первая строка — заголовок.
- `divider`: только `type`.
- `html`: `html` — произвольная разметка, **чистится** на сервере по allowlist
  (см. ниже; `div/span/figure/figcaption` и атрибут `class` разрешены, чтобы
  блок оставался настоящим «своим HTML», а не вторым `text`).

Неизвестный `type`, лишние ключи и значения не тех типов — ошибка поля, запись
не сохраняется (как у остальных полей).

**Пустые блоки не сохраняются**: блок с пустым `heading`/`text`/`html`, картинка
без `image`, галерея без картинок, цитата без текста, таблица без строк —
молча отбрасываются при сохранении (редактор добавляет пустой блок первым
действием, и он не должен попадать в данные). Таблица с одной строкой
(заголовком) валидна; строки могут быть разной длины.

**Нормализация**: сохраняем только известные ключи; `level` у заголовка по
умолчанию `2`; пустые `alt`/`caption`/`link`/`author` не пишем вовсе. Значение
поля отдаётся массивом; совсем пустое значение — обычный `null` для пустого
списка, как у остальных полей.

**Ссылки проверяются сервером**: `image.link` и `image`/`images[].image`
допускают только `http(s)://`, `/…` и `#…`; `javascript:` и прочее — ошибка.
В `html`-блоке `a[href]` и `img[src]` проходят те же схемы (внутри allowlist
`ammonia`). Существование файла в `files` не проверяется: путь может быть
внешним или прийти из импорта.

## Отдача в bxapi

Поле приходит в `properties` массивами как есть — фронт получает JSON, ничего
не рендерим. Для поля видны только разрешённые ключи; `html` уже очищен на
сохранении. `field_values` попадает в `search_vector`: текст блоков ищется
(теги `html`-блока тоже попадут в индекс — TD).

## Админка

- В форме записи поле `blocks` — свой редактор: список блоков, у каждого
  заголовок типа и поля; кнопки вверх/вниз и drag&drop, дублировать, удалить;
  «Добавить блок» — меню типов.
- Состояние редактора живёт в hidden-поле JSON; сервер разбирает и валидирует.
- Картинки: кнопка «Загрузить» шлёт файл на
  `POST /admin/blocks/upload?collection=ID` (multipart, только изображения,
  лимит 10 МБ) и получает `{ "path": "/upload/…" }`. Право — запись в эту
  коллекцию (`require_collection(…, Write)`), как у правки записи; без
  `collection` — 400. Файл сохраняется общим механизмом `files`/`upload_dir`.
- Редактор — ванильный JS (`static/admin/blocks.js`), без сборщика, как
  `admin.js`/`list.js`. При отключённом JS поле остаётся текстовым JSON.

## Очистка HTML

`ammonia` (html5ever): разрешены `p, br, strong, b, em, i, u, s, a[href], ul, ol,
li, blockquote, table, thead, tbody, tr, td, th, h2, h3, h4, img[src|alt],
div, span, figure, figcaption`; у `div/span/figure/figcaption` разрешён
`class` (без `style`); ссылки — только `http(s)://`, `/`, `#`; `script`,
`iframe`, `on*` невозможны. Если после очистки не осталось разметки —
сохраняется пустая строка, а пустой блок отбрасывается общим правилом.
Очистка на сохранении, а не на отдаче.

## Файлы

- `migrations/` — не нужна: значение поля хранится в существующем JSONB.
- `src/collection/fields.rs` — kind `blocks`, разбор формы и валидация.
- `src/collection/blocks.rs` — модель блоков, валидация, очистка HTML, сериализация.
- `src/admin/blocks.rs` — загрузка картинки блока.
- `templates/admin/item_form.html` — control для `blocks`.
- `static/admin/blocks.js` — редактор.
- `src/bxapi/` — сериализация поля в ответе.
- `Cargo.toml` — `ammonia`.

## Проверка

TDD: разбор значения (валидный массив, неизвестный тип, лишний ключ, битый JSON,
пустое значение); очистка `html` (script/iframe/onclick вырезаны, разрешённое
осталось); bxapi отдаёт массив; сохранение через админку пишет JSON и видно в
версии; загрузка картинки возвращает путь; не-изображение отклоняется.

## Решения по вопросам исполнителя (мои, можно оспорить)

1. Allowlist расширен `div/span/figure/figcaption` + `class`; очистка в пустоту — не ошибка.
2. Загрузка блоков требует `?collection=ID` и права записи в коллекцию.
3. Пустые блоки отбрасываются; таблица из одной строки валидна, строки могут быть разной длины.
4. Схемы ссылок проверяются сервером и для `image.link`, и внутри `html`.
5. Путь картинки — `/upload/…` или `http(s)://…`; существование файла не проверяется.
6. Нормализация на сохранении: только известные ключи, `level` по умолчанию 2, пустые необязательные поля не пишутся.

## Что решает план

Порядок работ: модель и валидация → kind поля и сохранение → bxapi → загрузка →
редактор JS → тесты.
