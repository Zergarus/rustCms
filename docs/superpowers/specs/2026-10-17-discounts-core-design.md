# Скидки: ядро — дизайн

Дата: 2026-10-17. Подпроект 3а серии «до функционала Битрикса „Бизнес“»
(коллекции → SKU → обмен с 1С: каталог и заказы → **скидки: ядро** → скидки: накопительные,
подарки, округление (3б) → …).

CMS — универсальный шаблон под любой проект (как сам Битрикс): объём и поведение задаёт
паритет с правилами работы с корзиной модуля `sale` Битрикса (`Sale\DiscountBase`,
`sale/general/sale_cond.php`, `sale/general/sale_act.php`, `catalog/general/catalog_cond.php`,
`Sale\DiscountCouponsManagerBase`).

## Цель и критерии успеха

Скидки и наценки считаются так же, как в Битриксе, и видны в корзине, итогах формы, заказе,
письмах, истории заказов, админке и выгрузке в 1С; правила и купоны переносятся из Битрикса.

Готово, когда:

- движок на эталонных примерах (по коду Битрикса) даёт те же цены, что Битрикс;
- на копии dev-базы перенесённые правила (4 активных правила трансопта: ±10 % и ±5 % для
  групп пользователей на товары со значением свойства) дают ожидаемые цены корзины,
  итогов формы и заказа;
- купон применяется и снимается через API, одноразовый после заказа больше не действует;
- фронт работает без изменений; без активных правил ответы bxapi и `/api/v1` байт в байт
  совпадают со сборкой до скидок.

Не входит (3б): накопительные скидки (`CondCumulativeGroup`, `b_catalog_disc_save_*`),
подарки (`ActSaleGift`), правила округления цен. Не входит вообще: старые скидки модуля
каталога (`b_catalog_discount`) — только предупреждение при переносе; перенос исторических
заказов.

## Данные — миграция `0019_discounts.sql`

- `discounts`: `id`, `name`, `active`, `active_from`, `active_to` (TIMESTAMPTZ NULL),
  `priority INT` (по умолчанию 1), `sort INT` (100), `last_discount BOOL` (прекратить
  дальнейшее применение), `last_level_discount BOOL` (не применять правила с меньшим
  приоритетом), `use_coupons BOOL` (только по купону), `conditions JSONB`, `actions JSONB`,
  `unsupported TEXT NOT NULL DEFAULT ''` (классы, которые движок не знает; правило с ними не
  применяется), `xml_id`, `created_at`, `updated_at`.
- `discount_groups (discount_id, group_id)`; правило без групп — для всех.
- `discount_coupons`: `id`, `discount_id`, `coupon TEXT UNIQUE`, `active`, `active_from`,
  `active_to`, `kind` (`basket` — одноразовый на позицию, `order` — одноразовый на заказ,
  `multi` — многоразовый; как `TYPE` 1/2/4 Битрикса), `max_use INT` (0 — без лимита),
  `use_count INT`, `user_id` (NULL — любому), `description`.
- `buyer_coupons (buyer_id, coupon_id, added_at)` — купоны корзины до оформления.
- `cart_items`: `base_price NUMERIC(18,2)` (цена до скидок), `discount_price NUMERIC(18,2)`
  (скидка на единицу; наценка — отрицательная); `price` — итоговая.
- `shipments.base_price` — цена доставки до скидок.
- `order_discounts`: `order_id`, `discount_id` (NULL, если правило удалено), `name`,
  `coupon`, `applied JSONB` (позиции `{cart_item_id, value}` и доставка), `sum`.
- Право `discounts.manage` «Скидки» в `access.rs`.

## Условия и действия

Дерево — JSON по формату Битрикса: `{ "CLASS_ID", "DATA", "CHILDREN" }`; значения `DATA` —
как в Битриксе (`All`: `AND`/`OR`, `True`: `True`/`False`, `logic`: `Equal`/`Not`/`Great`/
`Less`/`EqGr`/`EqLs`/`Contain`/`NotCont`, `value`). Ссылки на сущности — наши id (коллекции,
поля, записи, разделы, варианты списков, группы, платёжки, доставки, типы плательщика).

Условия заказа (`conditions`):

| Класс | Смысл |
|---|---|
| `CondGroup` | группа И/ИЛИ, истинно/ложно |
| `CondBsktCntGroup`, `CondBsktAmtGroup`, `CondBsktAmtBaseGroup` | количество / сумма / сумма по базовой цене позиций, подходящих под вложенные условия |
| `CondBsktProductGroup` | в корзине есть (нет) позиции под вложенные условия |
| `CondBsktRowGroup` | число строк корзины |
| `CondBsktSubGroup` | подгруппа условий строки |
| `CondBsktFldProduct`, `CondBsktFldName`, `CondBsktFldPrice`, `CondBsktFldQuantity`, `CondBsktFldSumm`, `CondBsktFldWeight` | поля строки |
| `CondIBElement`, `CondIBIBlock`, `CondIBSection`, `CondIBXmlID`, `CondIBName`, `CondIBCode`, `CondIBProp:<коллекция>:<поле>` | товар строки (у предложения — и родитель, как в Битриксе) |
| `CondCatQuantity`, `CondCatWeight` | количество на складе, вес товара |
| `CondSaleOrderSumm`, `CondSaleOrderWeight`, `CondSalePersonType`, `CondSalePaySystem`, `CondSaleDelivery`, `CondSaleCmnDayOfWeek` | заказ |
| `CondBsktAppliedDiscount` | к позиции уже применена скидка |

Действия (`actions`), константы `CSaleActionCtrlBasketGroup` / `CSaleActionCtrlDelivery`:
`ActSaleBsktGrp` — на позиции под вложенными условиями, `Type` `Discount` (скидка) /
`Extra` (наценка) / `Closeout` (установить цену), `Unit` `Perc` / `CurEach` (на каждую
единицу) / `CurAll` (сумма, распределяемая пропорционально стоимости позиций), `Max`
(не больше; с `CurAll` не используется); `ActSaleSubGrp` — подгруппа действий;
`ActSaleDelivery` — доставка, `Type` `Discount` / `DiscountZero` / `Extra`, `Unit` `Perc` /
`Cur`.

Неизвестный класс в дереве: правило не применяется, `unsupported` перечисляет классы,
админка показывает предупреждение.

## Порядок применения (`Sale\DiscountBase`)

1. Подходящие правила: активные, в датах, группа пользователя пересекается с группами
   правила (или групп нет), `unsupported` пусто, при `use_coupons` — активный купон правила
   у покупателя.
2. Сортировка: `priority` по убыванию, затем `sort`, затем `id`.
3. Правило проверяет `conditions` по текущему состоянию корзины и применяет `actions` к
   текущим ценам (каждое следующее — от цены после предыдущих).
4. `last_discount` у сработавшего правила останавливает всё дальнейшее;
   `last_level_discount` — правила с меньшим приоритетом.
5. Цена позиции не становится отрицательной; позиции с `custom_price` не участвуют.
6. Деньги округляются до копеек на каждом шаге, как `Sale\PriceMaths::roundPrecision`.

Движок — чистая функция `discount::calculate(rules, &Context) -> DiscountResult` без БД:
`Context` — позиции (id, товар и его данные для условий, базовая цена, количество,
custom_price), пользователь и группы, купоны, сумма и вес заказа, платёжка, доставка и её
цена, тип плательщика, день недели; `DiscountResult` — цена и скидка по каждой позиции,
цена доставки, применённые правила и купоны с суммами.

## Где считается и хранится

- **Корзина:** пересчёт на каждом чтении (bxapi `basket`, итоги формы, оформление) с
  записью `base_price`/`discount_price`/`price` у позиций корзины.
- **Итоги формы:** «Стоимость товаров» — по базовой цене, «Скидка» — при скидке > 0 (как
  `BitrixSaleOrderSummarySource`), «Доставка» — со скидкой, «Итого».
- **Оформление:** скидки фиксируются в позициях и отгрузке, `order_discounts` записывается,
  купоны заказа: одноразовые деактивируются, у многоразовых растёт `use_count`
  (лимит проверяется при оформлении). Отмена заказа купоны не возвращает.
- **Правка заказа в админке** скидки не пересчитывает; «Пересчитать скидки» в карточке
  заказа применяет текущие правила к позициям заказа.
- **Письма и история:** суммы скидки и базовая цена (`basePrice` позиции в истории —
  настоящая базовая).
- **Каталог:** цена со скидкой товара — правила, у которых условия зависят только от
  товара и пользователя (без условий корзины и заказа), применённые к одной единице (как
  `GetOptimalPrice`). `/api/v1` — поле `price_discount`; bxapi — только при флаге проекта.
- **Купоны в API (bxapi):** `POST /basket/coupon/add {coupon}`, `POST /basket/coupon/remove
  {coupon}`, в ответе `basket` — список купонов (`coupons: [{coupon, status, text}]`, только если у
  покупателя есть купоны — иначе ответ прежний байт в байт).
  Ошибки — тексты `DiscountCouponsManager` Битрикса (не найден, не активен, истёк,
  использован).
- **1С:** выгрузка — `ЦенаЗаЕдиницу` со скидкой, у позиции `Скидки/Скидка` («Скидка на
  товар», сумма, `УчтеноВСумме=true`), у заказа — скидка на заказ (`getXmlOrderDiscount`);
  приём — цены из 1С как есть.

## Админка

Право `discounts.manage`: список правил (название, активность, приоритет, сортировка, даты,
группы, «только по купону», число купонов, предупреждение `unsupported`; включение из
списка); форма правила — поля, группы, конструктор дерева условий и действий (небольшой JS
без библиотек; дерево уходит JSON-полем; сервер проверяет классы и ссылки, ошибки — у узла,
введённое сохраняется); купоны правила — список, добавление, генерация пачки (количество,
префикс, тип, лимит, срок), выключение и удаление неиспользованных. Карточка заказа — блок
«Скидки» и «Пересчитать скидки».

## Перенос из Битрикса

`import-bitrix`: `b_sale_discount` (`CONDITIONS`/`ACTIONS` — PHP-serialize в JSON, id
инфоблоков, свойств, элементов, разделов, вариантов, групп, платёжек, доставок — на наши;
неизвестные классы — в `unsupported`), `b_sale_discount_group`, `b_sale_discount_coupon`.
Строки `b_catalog_discount` — предупреждение со списком, не переносятся.

## Модуль проекта

`DiscountConditionHook` — свои классы условий: `class_ids()` и `check(class_id, data,
&Context, позиция) -> Option<bool>` (как `OnCondSaleControlBuildList`); флаг цены со скидкой
в каталоге bxapi. Для трансопта не заполняется.

- Модульные тесты движка: каждый класс условий и действий, И/ИЛИ/ложно, `Max`,
  распределение `CurAll`, `Cur`, доставка, приоритеты, `last_discount`,
  `last_level_discount`, купонные правила, группы, даты, `custom_price`, неотрицательная
  цена, округление; четыре правила трансопта.
- `sqlx::test`: пересчёт корзины, итоги со «Скидкой», фиксация в заказе и `order_discounts`,
  купоны (одноразовые, многоразовые с лимитом, истёкший, чужой, неактивное правило, повтор),
  отмена заказа, «Пересчитать скидки», `price_discount` в `/api/v1`, выгрузка в 1С со
  `Скидками`, перенос (замена id, неподдерживаемый класс, предупреждение каталога).
- Сквозная проверка на копии dev-базы: перенос правил трансопта из локального Битрикса
  (только чтение), корзина пользователя группы с наценкой и без группы, купон через bxapi,
  итоги и оформление, история и XML для 1С.
- Регрессия на основной базе без активных правил: bxapi и `/api/v1` байт в байт.
- В локальный Битрикс запросы с побочными эффектами не отправляются.
