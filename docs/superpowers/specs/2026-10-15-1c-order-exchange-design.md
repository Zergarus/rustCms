# Обмен с 1С: заказы — дизайн

Дата: 2026-10-15. Подпроект 2б серии «до функционала Битрикса „Бизнес“»
(коллекции → SKU → обмен с 1С: каталог (2а) → **обмен с 1С: заказы** → скидки → …).
Опирается на обмен каталогом (`2026-10-10-1c-catalog-exchange-design.md`): протокол,
сессии, вход, zip, лимиты, журнал и настройки модуля `exchange` переиспользуются.

CMS — универсальный шаблон под любой проект (как сам Битрикс), поэтому объём и умолчания
задаёт паритет с модулем `sale` Битрикса (`sale.export.1c`, `CSaleExport`,
`CSaleOrderLoader`), а не настройки конкретного сайта.

## Цель и критерии успеха

1С обменивается заказами с CMS так же, как с Битриксом: в настройках обмена 1С
указывается адрес CMS. Сайт отдаёт новые и изменённые заказы в CommerceML 2.x
(версии `version` как у Битрикса: 2.05 по умолчанию, выше, 3.x с контейнерами) и принимает из 1С изменения заказов, оплат и отгрузок, а при включённых
опциях — новые заказы, оплаты и отгрузки.

Готово, когда:

- выгрузка заказа по составу элементов и значений совпадает с эталонами, составленными
  по коду `CSaleExport` для каждой поддерживаемой версии схемы;
- выгруженный и подтверждённый (`success`) заказ не выгружается повторно, пока его не
  изменят на сайте; изменения, пришедшие из 1С, не возвращаются в 1С;
- файл документов из 1С меняет статус, отмену, оплату, отгрузку и состав заказа по
  опциям, создаёт заказы, оплаты и отгрузки по опциям; ошибка одного документа не
  мешает остальным;
- сквозной прогон эмулятором 1С на копии dev-базы проходит, повтор файла не создаёт
  дублей;
- фронт и bxapi на основной dev-базе работают без изменений (ответы байт в байт).

Не входит: новая система обмена Битрикса (параметр `cmlVersion` ≥ 2.10, схема
«Документы.Подчинённые») и режимы Битрикс24/CRM (обмен счетами) — на них ответ `failure`
с понятным текстом;
перенос самих заказов из Битрикса (`b_sale_order` и связанные таблицы) — отдельный
пункт списка паритета; маркировка, кассовые чеки, НДС и скидки в документе (подпроекты
«Торговый каталог» и «Скидки»).

## Протокол

Адрес тот же: `/api/1c/exchange`, параметр `type=sale`. Вход, сессия (cookie
`CMS_1C_SID`, `sessid`), zip, `file_limit`, интервал и журнал — из 2а. Тексты ответов —
как у Битрикса.

| Запрос | Ответ |
|---|---|
| `checkauth` | Как в 2а; для `type=sale` нужно право `exchange.1c.sale` «Обмен заказами с 1С» (или суперадмин). |
| `init` | `zip=yes\|no\nfile_limit=<байты>`; если передан `version` — ещё `sessid=<токен>\nversion=2.09`, версия запоминается в сессии. `cmlVersion` ≥ 2.10 запоминается и приводит к `failure` на `query`/`import`. |
| `query` | XML заказов, `application/xml; charset=windows-1251`. |
| `success` | Подтверждает последнюю выгрузку сессии: `success`; без выгрузки в сессии — `error`. |
| `file` | Тело дописывается к файлу сессии (как в 2а). `success`. |
| `import` | Распаковка zip при первом обращении, затем разбор документов по шагам в пределах интервала: `progress` / `success` (+ тексты ошибок документов) / `failure\n<текст>`. |
| `info` | Справочники XML (windows-1251): статусы, активные платёжные системы с типом (наличный / безналичный / эквайринг), активные службы доставки. |

Версия схемы — число из `version` (как `CSaleExport::getVersionSchema`, запятая = точка),
без `version` — 2.05. Пороги, как в `general/export.php`: больше 2.05 — `НомерВерсии`,
`Номер1С`, единица измерения с кодом (796 по умолчанию), типы контактов «Телефон рабочий» /
«Электронная почта» (иначе «ТелефонРабочий» / «Почта»); от 2.10 — за заказом документы
оплат и отгрузок и документы удалённых отгрузок; от 3 — документы одного заказа в
`<Контейнер>`.

## Данные — миграция `0018_order_exchange.sql`

- `orders`: `id_1c TEXT NOT NULL DEFAULT ''`, `version_1c TEXT NOT NULL DEFAULT ''`,
  `updated_1c BOOLEAN NOT NULL DEFAULT FALSE` (изменение пришло из 1С; любое
  изменение заказа на сайте сбрасывает), `external BOOLEAN NOT NULL DEFAULT FALSE`
  (создан из 1С, не выгружается); индекс по непустому `id_1c`.
- `payments`: `id_1c`, `version_1c`, `pay_voucher_num`, `pay_voucher_date DATE`,
  `is_return BOOLEAN`, `return_comment`, `updated_1c`.
- `shipments`: `id_1c`, `version_1c`, `allow_delivery BOOLEAN`, `allow_delivery_at`,
  `deducted BOOLEAN` («отгружена»), `deducted_at`, `delivery_doc_num`,
  `delivery_doc_date DATE`, `tracking_number`, `updated_1c`.
- `shipments_removed` — удалённые отгрузки (заказ, id, `id_1c`, время) для документов
  удалённых отгрузок, как `SHIPMENT_REMOVED` у Битрикса; заполняется триггером.
- `users.xml_id TEXT NOT NULL DEFAULT ''` + уникальный индекс по непустому.
- `person_types.domain CHAR(1) NOT NULL DEFAULT 'I'` (`I` — физлицо, `E` — юрлицо;
  `b_sale_bizval_persondomain`).
- `exchange_order_map` — соответствие реквизитов: `person_type_id`, `code` (код
  Битрикса: `BUYER_PERSON_*` / `BUYER_COMPANY_*` или `1C_REKV_<n>` — произвольный реквизит),
  `name` (для `1C_REKV_*`),
  `source` (`property` / `user` / `order` / `value`), `value` (id свойства, поле
  пользователя или заказа, константа). Аналог `b_sale_bizval` с потребителем «1C».
- `exchange_log.kind TEXT NOT NULL DEFAULT 'catalog'` (`catalog` / `sale`).
- Право `exchange.1c.sale` в `access.rs`.

Сброс `updated_1c`: все пути изменения заказа на сайте (оформление, админка, смена
статуса, оплата, отмена, правка позиций и свойств, ЮKassa) ставят `updated_1c = FALSE`
и обновляют `updated_at`; изменения обмена ставят `updated_1c = TRUE`.

## Выгрузка (`query`)

Отбор, как `sale.export.1c`: `updated_1c = FALSE`, `external = FALSE`,
`updated_at >= ` подтверждённой метки (настройка `sale_last_export_committed`, пусто —
без ограничения); фильтры настроек: только оплаченные; только с разрешённой доставкой
(есть отгрузка с `allow_delivery`); статусы начиная с заданного (по `sort` статусов).
Порядок `updated_at, id`. За один `query` — заказы, уложившиеся в интервал (0 — все).
Максимальный `updated_at` выгруженных заказов запоминается в сессии; `success` пишет его
в `sale_last_export_committed`. `query` без `success` отдаёт те же заказы снова.

Документ заказа (`КоммерческаяИнформация ВерсияСхемы ДатаФормирования` → `Документ`):
Ид (id), Номер (префикс + `account_number`), Дата, Время, ХозОперация «Заказ товара»,
Роль «Продавец», Валюта (с заменой из настройки), Курс 1, Сумма, Комментарий,
Номер1С и НомерВерсии (если есть); `Контрагенты`; `Товары` — Ид (`xml_id` записи, у
предложения `товар#характеристика`), ИдКаталога (`xml_id` коллекции), Наименование,
БазоваяЕдиница (код и название из `cml2_base_unit`, по умолчанию 796 «шт»),
ЦенаЗаЕдиницу, Количество, Сумма, реквизиты ВидНоменклатуры / ТипНоменклатуры
«Товар»; доставка — строка-услуга «ORDER_DELIVERY» «Доставка заказа»; `Склады`, если у
отгрузки есть склад; `ЗначенияРеквизитов`: Метод оплаты, Метод оплаты ИД, Заказ
оплачен, Дата оплаты, Доставка разрешена, Дата разрешения доставки, Способ доставки,
Отменен, Дата отмены заказа, Причина отмены, Финальный статус, Статус
заказа, Статуса заказа ИД, Дата изменения статуса, Сайт, Адрес доставки, произвольные
реквизиты из соответствия и реквизиты модуля проекта.

От версии 2.10 за заказом идут документы оплат (ХозОперация «Выплата безналичных денег» /
«Выплата наличных денег» / «Эквайринговая операция» по типу платёжной системы) и
отгрузок («Отпуск товара», с товарами отгрузки и строкой доставки), у каждого
`Основание` = Ид заказа, Ид = `id_1c` или наш id, свои реквизиты (Оплачен, Дата оплаты,
Номер платёжного документа, Признак возврата; Доставка разрешена, Отгружен, Номер и
дата отгрузки, Идентификатор отправления).

Контрагент: Ид — `users.xml_id` (пустой генерируется при выгрузке один раз, как в
Битриксе: `<id>#<логин>#<ФИО>`), гость без пользователя — от id заказа; физлицо —
Наименование, ПолноеНаименование, Фамилия/Имя/Отчество, Адрес регистрации; юрлицо —
ОфициальноеНаименование, ИНН, КПП, ЮридическийАдрес, РасчетныеСчета, ОКПО;
Контакты (телефон, почта), Представители (контактное лицо), Роль «Покупатель».
Значения — по соответствию реквизитов типа плательщика; поля без соответствия
берутся по умолчанию, как в Битриксе (почта — `users.email`, имя — плательщик,
телефон и адрес — свойства с флагами `is_phone` / `is_address`, город — `is_location`).

Выгрузка строится в UTF-8 и перекодируется в windows-1251; символы вне кодировки —
`?` (как `Encoding::convertEncoding`).

## Приём (`file` + `import`)

Файл разбирается потоково; каждый `Документ` — своя транзакция (документы одного
`Контейнер` — одна общая, в порядке следования); `Контрагенты` до
документов запоминаются для создания заказов. Тип документа — по `ХозОперация`.
Ошибки документов накапливаются и возвращаются в ответе и журнале. Всё, что меняет
обмен, ставит `updated_1c = TRUE`. Документ с `НомерВерсии` не новее сохранённого
`version_1c` пропускается.

Поиск: заказ — по Ид = id, затем по `id_1c`, затем по номеру без префикса; оплата и
отгрузка — по `id_1c`, затем по нашему id; их заказ — по `Основание` (теми же
правилами).

- **Заказ товара, найден:** записываются `id_1c` (Номер1С/Ид из 1С) и `version_1c`;
  «Статуса заказа ИД» меняет статус при включённой опции «Менять статус из 1С» (история
  с комментарием «1С», письмо о смене статуса — как при обычной смене); «Отменен» =
  `true` / `false` — отмена / снятие отмены через `set_canceled` (остатки);
  `ПометкаУдаления` — отмена. Состав (количества, цены, удалённые и новые строки по
  `xml_id`) правится при опции «Обновлять количество в корзине»: остатки через
  `stock::plan`, суммы заказа пересчитываются. Оплаченный или отгруженный заказ по
  составу не правится — ошибка «заказ в финальном состоянии».
- **Заказ товара, не найден:** при «Создавать новые заказы» — заказ с
  `external = TRUE`: покупатель по `Контрагент` (по `users.xml_id`, иначе новый
  пользователь без пароля с этим `xml_id`), тип плательщика по домену контрагента
  (юрлицо при ИНН/ОфициальноеНаименование), позиции по `xml_id`, статус по умолчанию,
  свойства по соответствию реквизитов (в обратную сторону); при «Создавать отгрузку
  для нового заказа» — отгрузка службой по умолчанию. Иначе — ошибка «заказ не найден».
- **Оплата, найдена:** «Оплачен» = `true` — оплачена (дата и номер по 1С); «Признак
  возврата» — снятие оплаты с причиной; `ПометкаУдаления` удаляет неоплаченную,
  оплаченную оставляет с ошибкой. `orders.paid` = все оплаты оплачены.
- **Оплата, не найдена:** при «Создавать новые оплаты» — новая оплата заказа:
  платёжная система по умолчанию для наличных / безналичных / эквайринга, при оплате
  заказа целиком — «по умолчанию для оплаченного заказа». Иначе — ошибка.
- **Отгрузка, найдена:** «Дата отгрузки по 1С» — отгружена (номер, дата, трек);
  «Доставка разрешена»; при заданном «Статусе при отгрузке» заказ переходит в него.
  Расхождение количеств с позициями: при «Обновлять количество в корзине» — правка
  позиций (правила заказа), иначе ошибка. Отгрузка не списывает остатки повторно
  (списание — при оформлении, `stock_deducted`). `ПометкаУдаления` удаляет
  неотгруженную, отгруженную оставляет с ошибкой.
- **Отгрузка, не найдена:** при «Создавать новые отгрузки» — новая отгрузка службой по
  умолчанию. Иначе — ошибка.

Неизвестная `ХозОперация` — ошибка документа. После каждого документа — хук
`after_import_order`.

## Настройки (`options`, модуль `exchange`, ключи `sale_*`) и админка

Умолчания — как в коде Битрикса.

| Настройка | Аналог | По умолчанию |
|---|---|---|
| Выгружать только оплаченные | `1C_EXPORT_PAYED_ORDERS` | нет |
| Выгружать только с разрешённой доставкой | `1C_EXPORT_ALLOW_DELIVERY_ORDERS` | нет |
| Выгружать начиная со статуса | `1C_EXPORT_FINAL_ORDERS` | все |
| Замена валюты | `1C_REPLACE_CURRENCY` | пусто |
| Префикс номера заказа | `1C_SALE_ACCOUNT_NUMBER_SHOP_PREFIX` | пусто |
| Менять статус из 1С | `1C_CHANGE_STATUS_FROM_1C` | нет |
| Статус при отгрузке | `1C_FINAL_STATUS_ON_DELIVERY` | не задан |
| Обновлять количество в корзине | `1C_IMPORT_UPDATE_BASKET_QUANTITY` | да |
| Создавать новые заказы | `1C_IMPORT_NEW_ORDERS` | да |
| Создавать новые оплаты | `1C_IMPORT_NEW_PAYMENT` | да |
| Создавать новые отгрузки | `1C_IMPORT_NEW_SHIPMENT` | да |
| Отгрузка для нового заказа | `1C_IMPORT_NEW_ORDER_NEW_SHIPMENT` | да |
| Платёжная система: наличные / безналичные / эквайринг / оплаченный заказ | `1C_IMPORT_DEFAULT_PS`, `_B`, `_A`, `_ORDER_PAID` | не задана |
| Служба доставки по умолчанию | `1C_IMPORT_DEFAULT_SHIPMENT_SERVICE` | не задана |

Интервал, лимит файла и zip — общие с каталогом.

Страница «Обмен с 1С»: вкладки «Каталог» и «Заказы» (настройки выше); «Соответствие
реквизитов» по типам плательщика (домен физлицо/юрлицо, поля контрагента, произвольные
реквизиты); журнал — общий, с колонкой «тип» и счётчиками заказов / оплат / отгрузок
(выгружено / создано / изменено). Право на страницу — `exchange.1c` или
`exchange.1c.sale` (каждый видит свою вкладку).

Карточка заказа в админке: блок «1С» (Номер1С, версия, «изменён из 1С», «создан в
1С»; у оплат и отгрузок — номера, даты, трек) и «Выгрузить XML для 1С» — документ
заказа без побочных эффектов (Ид контрагента не сохраняется, метка не двигается).

## Перенос из Битрикса

`import-bitrix` переносит: опции `sale/1C_*` → настройки `sale_*`;
`last_export_time_committed_*` → `sale_last_export_committed`; `b_sale_bizval` с
потребителем `1C` (с подстановкой `COMMON` и типа плательщика 0) → `exchange_order_map`;
`b_sale_bizval_persondomain` → `person_types.domain`; `b_user.XML_ID` → `users.xml_id`.

## Модуль проекта

Точки расширения `Project` (по образцу `after_import_item`):
`export_order_traits(&OrderView) -> Vec<(String, String)>` — свои реквизиты документа
заказа; `after_import_order(&mut tx, order_id, &RawDocument)` — свой разбор документа
из 1С (аналог событий обмена Битрикса). По умолчанию пустые.

## Проверка

- Модульные тесты выгрузки на рукописных эталонах в `tests/fixtures/1c/sale/`:
  физлицо, юрлицо с ИНН/КПП и счётом, гость, предложение `#`, доставка, склад, версия
  2.05 (без `version`), 2.08, 2.10 с оплатой и отгрузкой, 3.1 с контейнером, отменённый заказ, замена
  валюты, префикс, windows-1251 и символ вне кодировки, реквизиты соответствия и
  модуля проекта.
- `sqlx::test` отбора: новый заказ уходит; после `success` — нет; после правки на сайте
  (каждый путь изменения) — снова; изменение из 1С не возвращает в выборку; `query` без
  `success` повторяется; фильтры оплачен / доставка / статус; `external` не уходит;
  интервал.
- `sqlx::test` приёма: статус с опцией и без, письмо; отмена и снятие (остатки);
  пометка удаления; старая версия пропущена; состав при опции (остатки, суммы) и без;
  финальный заказ не правится; новый заказ с новым и существующим контрагентом; оплата
  найдена / создана / возврат / удаление; отгрузка отгружена / трек / статус при
  отгрузке / создана / расхождение; ошибка одного документа не мешает остальным;
  повтор файла без дублей.
- Тесты протокола через роутер: право `exchange.1c.sale` (и что `exchange.1c` его не
  даёт); `init` с `version` и без; `info`; `success` без выгрузки → `error`; `file` +
  `import` частями и в zip; файл с `Контейнер`; `cmlVersion` 2.10 → `failure`.
- Сквозной прогон эмулятором 1С на копии dev-базы (`CREATE DATABASE … TEMPLATE`):
  выгрузка заказов, `success`, ответный файл с изменениями заказа, оплаты и отгрузки,
  новый заказ из 1С, повтор без дублей; копия удаляется, тестовые заказы основной базы
  не трогаются.
- Регрессия на основной dev-базе: фронт, ответы bxapi байт в байт; оформление заказа на
  фронте даёт `updated_1c = FALSE`.
- В локальный Битрикс запросы с побочными эффектами не отправляются.
