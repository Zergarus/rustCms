# Формы как конфигурация

Цель: перенести архитектуру форм модуля `mediagroup.bxapi`, а не отдельные фичи.
Сейчас форма — это Rust-структура в `project/mod.rs`: чтобы добавить отзывы,
заявку или бриф, проект пересобирается. Для продукта форма должна описываться
данными, а проект — добавлять свои формы без правок ядра.

## Референс: как это сделано в Битриксе

- `FormDefinition` = валидатор + необязательные writer и notifier; любой шаг
  заменяется классом проекта.
- `FormRegistry`: дефолты модуля (`.settings.php` → `forms`) → оверрайд проекта
  (`/bitrix/.settings.php` → `bxapi.forms`) → рантайм `register()`.
- Один эндпоинт `POST /api/v1/form/{code}`, ответ `{id, data}`, ошибки валидации
  с HTTP 400 и `errors[0].code`.
- Валидатор по умолчанию умеет только `required` и `email`; файлы — по
  `allowedFiles`, запись файлов — `fileMapping`, списки — по `XML_ID` варианта.

## Что делаем (инкремент 1)

1. **Файл конфигурации** `config/forms.toml` (путь из `FORMS_CONFIG`), читается
   при старте. Оверрайд по коду формы целиком — как второй уровень реестра в
   Битриксе. Формат TOML требует одну новую зависимость — крейт `toml`; JSON
   обошёлся бы без неё, но конфиг с комментариями удобнее для проекта.
2. **Формат** повторяет структуру модуля, но в TOML:

```toml
[forms.callback.fields.name]
rules = ["required"]

[forms.callback.fields.contacts]
rules = ["required"]

[forms.callback.writer]
collection = "callback"

[forms.callback.writer.mapping]
name = "NAME"
contacts = "CONTACTS"

[forms.callback.files]
attachment = "FILES"

[forms.callback.notifier]
event = "CALLBACK_FORM"

[forms.callback.notifier.mapping]
name = "AUTHOR"
contacts = "TEXT"
```

3. **Реестр:** формы из `project/mod.rs` собираются как раньше, файл их
   дополняет и переопределяет по коду. Форма без writer/notifier допустима —
   соответствующий шаг пропускается.
4. **Валидация:** `required`, `email` (семантика модуля: `email` проверяется,
   только если значение пришло). Неизвестное правило — ошибка конфигурации при
   старте, а не молчаливое пропускание.
5. **Writer:** коллекция по `api_code`, маппинг поля формы → `NAME` /
   `PREVIEW_TEXT` / `DETAIL_TEXT` / код поля; файлы — через `files`.
6. **Notifier:** событие почты + маппинг, письмо уходит в фоне (как сейчас).
7. **Multipart:** один и тот же эндпоинт принимает JSON и `multipart/form-data`.
   Файлы сохраняются через `files::save`, в поле коллекции пишется id файла;
   расширения — по `files::allowed_extension`.
8. **Контракт не меняется:** тот же маршрут, тот же ответ `{id, data}`, те же
   ошибки. Формы проекта, описанные в коде, продолжают работать.

## Не входит (в техдолг)

- Кастомные валидатор/writer/notifier кодом проекта (trait) — пока только
  правила и маппинг из конфига.
- Списки по `XML_ID`: текущие формы проекта их не используют.
- Админка форм: конфиг правит разработчик проекта, как `.settings.php`.

## Файлы

- `src/bxapi/forms_config.rs` — serde-модель, загрузка файла, реестр.
- `src/bxapi/forms.rs` — валидация, запись, multipart.
- `src/state.rs` — реестр форм в `AppState`.
- `config/forms.toml.example` — образец для нового проекта.
- `src/forms_config_tests.rs` — тесты.

## Проверка (2026-11-10)

После ревью добавлено: `DefaultBodyLimit` 20 МБ на маршрут формы, лимиты 10 МБ
на файл и 5 файлов на заявку, отказ `file_not_allowed` на незаявленные файлы,
проверка файлового поля по схеме коллекции (существование, тип, множественность),
`deny_unknown_fields` и проверки конфига (пустые коллекция/событие/код, ключи
маппинга вне `fields`, пустая форма, `FORMS_CONFIG` без файла), общий троттлинг
форм (20 заявок с IP за 15 минут) и экранирование значений в HTML-письмах.

TDD: загрузка конфига; оверрайд кодовой формы файлом; неизвестное правило —
ошибка при старте; форма из файла пишет запись в коллекцию и шлёт письмо;
multipart с файлом сохраняет файл и id в поле; неизвестная форма — 404; ошибки
валидации не изменились; прежние JSON-формы проекта работают.
