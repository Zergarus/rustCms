# Замер производительности CMS против Битрикса и презентация

Дата: 2026-11-13. Статус: на согласовании.

## Зачем

Нужны воспроизводимые цифры «CMS против Битрикса» в равных условиях и
md-презентация для тимлида/руководителя: что уже работает, как устроено,
насколько быстро и где границы применимости. Старый
`docs/benchmark-bitrix-vs-rust.md` (2026-10-09) для этого не годится: Rust был
нативным процессом, Битрикс — через TLS/traefik, в php-fpm был Xdebug.

## Цели

- Сравнить одинаковые bxapi-ручки фронта на двух приложениях **в Docker**,
  за одинаковым nginx, с одинаковыми телами запросов и одним набором данных.
- Получить rps, p50/p95/p99, ошибки и память; сохранить методику и команды
  воспроизведения.
- Собрать `docs/presentation.md`: основные фичи админки со скриншотами,
  архитектура, API-совместимость, цифры производительности, ограничения и
  план P0.

## Не цели

- Не доказывать «Rust всегда быстрее»: сравниваем конкретный стенд и честно
  перечисляем ограничения.
- Не измерять запись (заказы, оплата, регистрация) — только чтение каталога,
  чтобы не менять данные и не смешивать сессии.
- Не настраивать production-тюнинг Битрикса глубже, чем «убрать dev-оверхед»:
  Xdebug off, OPcache/JIT on, разумный `pm.max_children`.
- Не менять код CMS и фронтенд.

## Выбранный подход

**App-to-app за одинаковым nginx, оба приложения в Docker.**

Отброшено:

- edge-to-edge через traefik+TLS: цифры включают TLS и разные прокси, хуже
  защищаются.
- только старые цифры: устарели и сняты в неравных условиях.

## Стенд

- Хост: Apple M4 Pro, 14 ядер, macOS, Docker Desktop. Оба стенда на одной
  машине, замеры по очереди, один генератор нагрузки.
- Bitrix: существующий `transopt.local` compose (nginx → php-fpm 8.3,
  MariaDB 10.11). Перед замером: Xdebug выключен, OPcache+JIT включены,
  `pm.max_children` поднят, `pm = static`/`dynamic` зафиксирован в отчёте.
- CMS: собранный `Dockerfile` образ, контейнер в той же Docker-сети, БД —
  существующий PostgreSQL 17 (тот же импорт из Битрикса).
- Перед обоими приложениями — nginx: у Битрикса штатный, у CMS — отдельный
  контейнер с `proxy_pass` на CMS. Оба HTTP, `Host: transopt.local`.
- CPU/память: по возможности одинаковые лимиты (`--cpus`, `--memory`) для
  приложений; если лимиты не ставим — фиксируем фактическое потребление.
- CSRF и rate-limit CMS на время замера выключены (`CSRF_ENFORCE=false`,
  `RATE_LIMIT_PER_MIN=0`); это указано в отчёте. Битрикс — без авторизации,
  как публичный API.

## Данные и запросы

Один набор данных: CMS импортирована из этой же Битрикс-базы. Перед замером
проверяем:

- одинаковый товар существует по одному id в обеих системах;
- количество элементов в списке и разделах совпадает или расхождение
  зафиксировано;
- поиск `U660` возвращает непустой результат в обеих системах.

Пять POST-запросов, тела — из фронта TransOpt:

| Ручка | Тело |
|---|---|
| `/api/v1/iblock/catalog/element/38382` | карточка товара, `select` как в `product/[id]` |
| `/api/v1/iblock/catalog/element/list` | список товаров, `limit: 20` |
| `/api/v1/iblock/catalog/section/list` | разделы с `hasElements` |
| `/api/v1/iblock/catalog/search` | поиск `U660`, `limit: 10` |
| `/api/v1/iblock/schemes/element/list` | схемы, `imageResize: [300, 800]` |

## Нагрузка

- Генератор: Python stdlib (`http.client`), keep-alive, фиксированное число
  запросов, N потоков. Запускается в контейнере в той же Docker-сети, чтобы не
  мерить сеть macOS.
- Прогрев: 30 запросов на ручку до замера.
- Замер: concurrency 8, 400–500 запросов на ручку; для медленного Битрикса
  время подбирается так, чтобы прогон шёл 10–30 с.
- Два прогона на ручку, в отчёт — медиана rps и p50/p95/p99; ошибки и
  не-200 — отдельной колонкой.
- Память: `docker stats --no-stream` до/после, для php-fpm и CMS; фиксируем
  RSS основного процесса, без БД.
- Результаты сырыми JSON — в `bench/results/`, сводка — в отчёт.

## Deliverables

- `bench/load.py` — генератор; `bench/payloads/*.json` — тела; `bench/run.sh` —
  воспроизводимый прогон с переменными URL.
- `docs/benchmark-v2.md` — стенд, методика, таблицы, ограничения, команды.
- `docs/presentation.md` — 10–15-минутный рассказ: проблема, архитектура,
  демо-фичи со скриншотами, API, цифры, ограничения, P0 и следующий шаг.
- Скриншоты — из `docs/design/` (существующие) + 3–4 свежих: дашборд,
  коллекция/запись, заказ, инструменты. Без фронтенда.

## Критерии приёмки

- Оба приложения отвечают 200 на все пять запросов до замера.
- В отчёте есть rps/p50/p95/p99 и ошибки по каждой ручке для обеих систем.
- Указаны версии/коммиты, конфиги PHP, лимиты Docker, дата и хост.
- Цифры воспроизводятся повторным запуском `bench/run.sh` (в пределах
  разумного разброса; разброс отражён).
- В презентации нет утверждений, не подкреплённых замером или кодом; явно
  сказано, что CRM вне скоупа и сравнение — только read-API.

## Риски

- Bitrix dev-стенд может остаться медленнее из-за MariaDB/PHP; это ограничение
  сравнения, а не «чистая» разница языков.
- Разные СУБД (MariaDB vs PostgreSQL) и разные объёмы кеша.
- Docker Desktop на macOS искажает абсолютные цифры; относительное сравнение
  на одном хосте остаётся полезным.
- Если данные в CMS и Битриксе разойдутся, сначала фиксируем расхождение,
  затем либо переливаем снимок, либо явно указываем отличие в отчёте.

## Что решает исполнитель

- Точные лимиты CPU/памяти и число запросов подбираются по факту, чтобы
  прогон не занимал часы; значения фиксируются в отчёте.
- Формат графиков в презентации: markdown-таблицы + 2–3 ASCII/PNG-графика,
  если получится без внешних зависимостей.
- Какие скриншоты админки взять, если существующих не хватает.
