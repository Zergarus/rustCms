# Админка, этап 3.2: массовые действия в списках — дизайн

Дата: 2026-11-05. Продолжение этапа 3 редизайна админки. Движок списков (этап 3.1:
`docs/superpowers/specs/2026-11-04-admin-lists-design.md`) уже в `main`: `src/admin/list/`,
`templates/admin/_list*.html`, `static/admin/list.js`. Ветка `feature/admin-bulk` от `main`.

## Цель и критерии успеха

Дать выполнять действия над многими записями списка сразу: отмеченными строками страницы
или всеми записями по текущему фильтру. Поведение каждого действия совпадает с одиночным
действием в карточке (письма, резервы, выгрузка в 1С, проверки прав).

Готово, когда:
- в списках записей коллекций и заказов есть колонка чекбоксов и панель действий;
- записи: «Активировать», «Деактивировать», «Перенести в раздел…», «Удалить»;
- заказы: «Сменить статус…», «Отметить оплаченным», «Снять оплату», «Отменить», «Снять отмену»;
- «Выбрать все N по фильтру» работает до 10 000 записей;
- каждая запись выполняется отдельно, итог показывает выполненное и причины невыполненного;
- для заказов в подтверждении есть галочка «Уведомить покупателей» (по умолчанию включена);
- пользователь без права на действие не видит его и получает 403 на прямой запрос;
- остальные списки и одиночные действия в карточках работают как раньше.

Вне рамок: правка значения поля у выбранных и редакторы значений (подпроект 3.3), выгрузка в
CSV/Excel, фоновое выполнение больших объёмов, действия в других списках админки.

## 1. Общие функции одиночных действий

Побочные эффекты одиночных действий сейчас живут в обработчиках (`src/admin/shop/orders.rs`
`set_status`, `set_paid`, `set_canceled`; `src/admin/items.rs` `delete`). Они выносятся в
функции, общие для карточки и массового действия:

- `src/sale/actions.rs` (новый модуль):
  ```rust
  pub enum MailEvent { StatusChanged(String), Paid, Canceled }   // имя события письма
  pub async fn change_status(db, id, status, user_id, comment) -> Result<Option<MailEvent>, ActionError>;
  pub async fn change_paid(db, id, paid) -> Result<Option<MailEvent>, ActionError>;
  pub async fn change_canceled(db, id, cancel, reason) -> Result<Option<MailEvent>, ActionError>;
  pub enum ActionError { NotFound, Rejected(String), Db(sqlx::Error) }
  ```
  Функции меняют заказ и возвращают письмо, которое надо отправить (или `None`): статус с
  `notify`, факт изменения, `paid = true`, `cancel = true` — правила те же, что сейчас в
  обработчиках. Неизвестный статус — `Rejected("Нет такого статуса")`; отгруженный заказ при
  отмене — `Rejected` с текстом из `StockError::Rejected`. Отправку (`mail::notify` через
  `tokio::spawn`) делает вызывающий: карточка — всегда, массовое действие — только при
  `notify = true`.
- Обработчики карточки переписываются на эти функции без изменения поведения.
- `src/collection/repo.rs`: `set_item_active(db, id, active) -> sqlx::Result<bool>` и
  `move_item(db, id, section: Option<i64>) -> sqlx::Result<bool>` (обновляют `updated_at`;
  `false` — записи нет). Удаление — существующая логика одиночного удаления, вынесенная в
  `items::delete_one(db, user, id) -> Result<(), ActionError>` (проверки
  `require_collection(Write)` и `require_parent_write`, затем `repo::delete_item`).

## 2. Описание массовых действий

`src/admin/list/bulk.rs`:

```rust
pub enum BulkParam { None, Choice(Vec<EnumOption>), Reason }  // статус/раздел; причина отмены
pub enum Confirm { Never, Always, Danger }
pub struct BulkAction { pub code: &'static str, pub label: String, pub param: BulkParam,
    pub confirm: Confirm, pub notify: bool }
```

- В `ListSpec` новое поле `bulk_actions: Vec<BulkAction>`. Построитель спеки кладёт только
  действия, разрешённые пользователю. Пустой список — нет колонки чекбоксов и панели.
- Записи коллекции (только при `collection_level >= Write`):
  - `activate` «Активировать», `deactivate` «Деактивировать» — без параметра, `Confirm::Never`;
  - `move` «Перенести в раздел…» — `Choice`: «Без раздела» (значение `none`) и разделы коллекции
    деревом (подпись с отступом по глубине), `Confirm::Always`;
  - `delete` «Удалить» — `Confirm::Danger`.
- Заказы (только при `orders.manage`):
  - `status` «Сменить статус…» — `Choice` из `order_statuses`, `notify: true`, `Confirm::Always`;
  - `paid` «Отметить оплаченным» — `notify: true`, `Confirm::Always`; `unpaid` «Снять оплату» —
    `Confirm::Always`;
  - `cancel` «Отменить» — `Reason` (необязательная), `notify: true`, `Confirm::Always`;
    `uncancel` «Снять отмену» — `Confirm::Always`.

Выполнение действия — функция обработчика списка:
`async fn run(ctx: &BulkCtx, action: &str, param: &str, id: i64) -> Result<(), String>`
(`Err` — причина для итога). Реестр по `list_key`: `orders` → функции заказов,
`collection:<id>` → функции записей (рядом с `views::spec_for_key`; при подключении следующего
списка заменяется общим реестром списков).

## 3. Запрос и выполнение

`POST /admin/lists/bulk`, форма:
`list_key`, `path`, `query`, `action`, `param`, `notify` (`1`/пусто), `scope` (`ids`|`filter`),
`ids` (через запятую, при `scope=ids`).

1. `spec_for_key` — доступ к списку (403/404 как у видов); `path` должен совпасть с путём
   списка для `list_key`.
2. Действие ищется в `spec.bulk_actions` пользователя — нет → 403. Параметр проверяется:
   значение из `Choice`, раздел этой коллекции, `Reason` не длиннее 500 символов; иначе 422.
3. Множество id: состояние из `query` разбирается движком (тот же `views::resolve` без
   восстановления и запоминания; открытый вид учитывается). `SELECT id <from> <joins> <where>
   [AND id = ANY($ids)] LIMIT 10001` — при `scope=ids` переданные id пересекаются с условием
   списка (чужие и скрытые фильтром молча отбрасываются), при `scope=filter` берутся все.
   Больше 10 000 → 422 «Слишком много записей: уточните фильтр (до 10 000)». Пустое множество →
   422 «Ничего не выбрано».
4. Каждый id — отдельный вызов `run` (своя транзакция внутри функций действий). Ошибка базы на
   записи → в итог «ошибка сервера», `tracing::error!`, обработка продолжается.
5. Письма заказов отправляются после выполнения каждой записи, если `notify = 1`.
6. Ответ — обновлённый `#list-body` для `path?query` (как `views::rerender`; перерисовка
   восстанавливает запомненные пользователем колонки, сортировку и размер страницы — тем же путём,
   что и действия над видами) и итог:
   - всё выполнено — уведомление «Готово: N»;
   - есть невыполненные — блок над таблицей (закрывается ✕): «Выполнено K из N. Не выполнено:»,
     причины сгруппированы, в каждой группе ссылки на записи (номер заказа или название записи,
     `open_url` спеки); больше 20 ссылок в группе — «и ещё M».

CSRF — общий `same_origin_guard`. Выполнение синхронное; 10 000 простых записей укладываются
в секунды, заказы с письмами — в десятки секунд.

## 4. Интерфейс

- **Колонка чекбоксов** слева (только при непустом `bulk_actions`). Клик — отметить строку;
  Shift+клик — диапазон от предыдущей отмеченной; клавиша X — текущая строка (J/K),
  Shift+X — диапазон. Чекбокс в шапке — вся страница; частичный выбор — `indeterminate`.
  Отмеченные строки подсвечены (оттенок, отличный от `tr.cur`).
- **Выбор живёт только на текущей странице** и сбрасывается при любом обновлении `#list-body`
  (фильтр, сортировка, страница, вид, `list:refresh`).
- **Панель действий** закреплена внизу списка, появляется при выборе:
  «Выбрано: N · Выбрать все 5 128 по фильтру · Действия ▾ · ✕».
  - «Выбрать все по фильтру» видна, когда отмечена вся страница и записей по фильтру больше;
    при `capped` (больше 10 000) вместо неё «Больше 10 000 — уточните фильтр».
  - После «Выбрать все» — «Выбраны все 5 128 по фильтру · Только эта страница».
  - ✕ и Escape снимают выбор.
- **Подтверждение** — поповер над панелью (без `confirm()`):
  - `Confirm::Never` и выбор строк — выполняется сразу;
  - «все по фильтру» — подтверждение всегда, с точным числом;
  - параметр — выпадающий список (статус, раздел) или поле причины;
  - `notify` — галочка «Уведомить покупателей», по умолчанию включена;
  - `Danger` — «Удалить 47 записей? Это нельзя отменить» и красная кнопка «Удалить 47».
- **Выполнение** — кнопка «Выполняется…» заблокирована, повторная отправка невозможна.
- **После** — новый `#list-body`, выбор сброшен, уведомление или блок итога.
- Без JS массовых действий нет; одиночные действия в карточках не меняются.
- На узком экране панель занимает всю ширину, элементы переносятся.

## 5. Ошибки

| Ситуация | Ответ |
|---|---|
| нет доступа к списку | 403/404 (как у видов) |
| действия нет у пользователя | 403, уведомление |
| неверный `path`, параметр, длинная причина | 422, уведомление с причиной |
| пустой выбор | 422 «Ничего не выбрано» |
| больше 10 000 по фильтру | 422 «Слишком много записей: уточните фильтр (до 10 000)» |
| запись не проходит (отгружен, нет права на товар, уже удалена) | в итог с причиной |
| ошибка базы на записи | в итог «ошибка сервера», лог |
| id вне фильтра | молча отбрасывается |

Ответы 4xx не подменяют список (HTMX не делает swap), уведомление — через `flash::toast`.

## 6. Тесты

- **Юнит:** разбор формы; группировка итога и обрезка «и ещё M»; проверка параметров действий.
- **Общие функции:** `sale::actions` возвращают те же письма, что прежние обработчики
  (статус с `notify` и без, повторная установка того же статуса, оплата, отмена); карточки
  заказа и записи после переноса ведут себя как раньше (существующие тесты остаются зелёными).
- **С базой, записи:** активировать/деактивировать/перенести/удалить по `ids` и по `filter`;
  перенос в раздел другой коллекции → 422; пользователь с `read` — нет `bulk_actions` и 403;
  удаление товара с предложениями — как одиночное; id из другой коллекции отбрасывается.
- **С базой, заказы:** решение «слать ли письмо» — чистая функция
  `bulk::mails_to_send(events, notify) -> Vec<MailEvent>`; тесты проверяют её и то, что
  действия возвращают ожидаемые `MailEvent` (смена статуса с `notify` у статуса и без, оплата,
  отмена); отмена с отгруженным заказом — он в итоге, остальные отменены.
- **Объём:** 10 001 запись по фильтру → 422; «все по фильтру» внутри открытого вида берёт
  записи вида.
- **Ответ:** фрагмент `#list-body` и уведомление; блок итога с группами и ссылками.
- **Браузер (Chrome):** чекбоксы, Shift+клик, X/Shift+X, панель, «Выбрать все по фильтру»,
  подтверждения (статус, удаление), итог с ошибками, сброс выбора при фильтре, узкий экран.
