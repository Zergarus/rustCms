# Складской учёт (ядро) — дизайн

Дата: 2026-10-27. Подпроект 5а серии «до функционала Битрикса „Бизнес“»
(коллекции → SKU → обмен с 1С → скидки 3а/3б → валюты → **склады: ядро (5а)** → склады:
штрихкоды, партии, API документов (5б) → SEO и поиск).

CMS — универсальный шаблон под любой проект (как сам Битрикс). Объём и поведение задаёт паритет с
модулем `catalog` Битрикса и местами списания и резерва в `sale`. Источники:
- документы: `CCatalogDocsTypes` и наследники (`general/store_docs_type.php`), действия
  `Document\Action\Store\*`, `Document\Action\Price\UpdateProductPricesAction`;
- остатки и резервы: `Product\CatalogProvider` (`shipProduct`, `shipQuantityWithStoreControl`,
  `shipQuantityWithoutStoreControl`, `getAutoShipStoreData`, `getDefaultStoreId`);
- условия резерва: `Sale\Order` (`ALLOW_DELIVERY`, `DEDUCTED`, оплата), `Sale\Configuration`,
  `Reservation\Configuration\ReserveCondition`, `Sale\ReserveQuantity`;
- автоснятие: `Sale\Helpers\ReservedProductCleaner`;
- обмен с 1С: `CIBlockCMLImport` (`QUANTITY` = количество из 1С − `QUANTITY_RESERVED`).

Работает в обоих режимах Битрикса — со складским учётом и без, переключение одной настройкой.

## Цель и критерии успеха

Магазин ведёт склады как Битрикс:
- со складским учётом остатки складов меняются документами (приход, оприходование, перемещение,
  возврат, списание), отгрузками и обменом с 1С;
- при условии резерва товар резервируется по складам;
- отгрузка списывает товар со склада отгрузки;
- без складского учёта остатки правятся вручную или обменом, резерв и списание идут от общего
  остатка товара.

Готово, когда:
- **Регрессия.** На копии основной базы со складским учётом выключенным сборки до и после
  подпроекта дают байт в байт одинаковые ответы bxapi и `/api/v1`: каталог, поиск, корзина,
  оформление заказа. Доступный остаток товара после оформления заказа тот же, что сейчас.
- **Сквозная проверка** на копии с перенесёнными складами и документами трансопта:
  1. приход;
  2. перемещение;
  3. заказ ставит резерв;
  4. отгрузка в админке уменьшает остаток склада и снимает резерв;
  5. снятие отгрузки возвращает остаток и резерв;
  6. отмена заказа снимает резерв;
  7. обмен с 1С: доступно = количество из 1С − резерв;
  8. автоснятие просроченного резерва.
- **Тесты** закрывают каждое правило ниже (раздел «Проверка»).

Не входит:
- штрихкоды (`BARCODE_MULTI`, `b_catalog_store_barcode`), партионный учёт (FIFO и средняя),
  API документов — это подпроект 5б;
- массовое проведение и печатные формы документов;
- инвентаризация (`I`), отмена резерва документом (`U`; в Битриксе — для резервов сделок CRM, у нас
  резервы привязаны к позициям заказа), документ реализации (`W`, CRM);
- наценка `BASE_PRICE_EXTRA`/`BASE_PRICE_EXTRA_RATE` (считает только интерфейс CRM);
- права на уход в минус по ролям (`check_rights_on_decrease_store_quantity` = `E`); работает режим
  по умолчанию `N` — минус разрешён товару с «можно покупать при отсутствии»;
- мастер включения учёта CRM (`StoreEnableWizard`: сброс остатков) — в коробке учёт включается
  флажком без сброса;
- журнал движений остатков.

## Модель остатков

Счётчики, как в Битриксе: значения хранятся и меняются на месте в одной транзакции с проверками.

- `catalog_store_amounts.amount` — физический остаток склада (`b_catalog_store_product.AMOUNT`).
- `catalog_store_amounts.quantity_reserved` — резерв на складе.
- `catalog_products.quantity` — доступно к покупке (`b_catalog_product.QUANTITY`).
- `catalog_products.quantity_reserved` — резерв товара.

Инварианты, которые поддерживает каждое изменение:
- **Со складским учётом:**
  - доступно = Σ `amount` по активным складам − резерв товара (`updateProductQuantity`);
  - резерв товара = Σ резервов его позиций;
  - резерв склада = Σ резервов позиций на этом складе.
- **Без складского учёта:**
  - `quantity` правится вручную или обменом с 1С;
  - резерв ставится и снимается на уровне товара: `quantity` −/+, `quantity_reserved` +/−;
  - склады не трогаются.

Товары без учёта количества (`quantity_trace` = нет) остатки не меняют, как сейчас.

## Данные — миграция `0023_stores`

- **`catalog_stores`:** добавить
  - `is_default BOOL` (не больше одного — частичный уникальный индекс);
  - `issuing_center BOOL` («пункт выдачи»);
  - `shipping_center BOOL` («отгрузочный склад»).
- **`catalog_store_amounts`:** добавить `quantity_reserved NUMERIC(18, 2) NOT NULL DEFAULT 0`.
- **`catalog_products`:** добавить
  - `quantity_reserved NUMERIC(18, 2) NOT NULL DEFAULT 0`;
  - `purchasing_price NUMERIC(18, 2)`;
  - `purchasing_currency TEXT`.
- **`basket_reservations`** (`b_sale_basket_reservation`): `id`, `cart_item_id` (позиция заказа,
  каскад), `store_id` (NULL — без склада), `quantity`, `date_reserve`, `date_reserve_end`,
  `reserved_by` (пользователь, NULL — система).
- **`basket_reservation_history`** (`b_sale_basket_reservation_history`): `id`, `reservation_id`,
  `date_reserve`, `quantity`.
- **`shipment_item_stores`** (`b_sale_store_barcode` без штрихкода): `shipment_id`, `cart_item_id`,
  `store_id`, `quantity`.
- **`contractors`** (`b_catalog_contractor`): `id`, `person_type` (юрлицо или физлицо),
  `person_name`, `company`, `inn`, `kpp`, `address`, `phone`, `email`, `post_index`, `created_at`,
  `updated_at`.
- **`store_documents`** (`b_catalog_store_docs`): `id`, `doc_type` (`A`/`S`/`M`/`R`/`D`), `title`,
  `doc_number`, `date_document`, `contractor_id`, `currency`, `total`, `items_order_date`,
  `items_received_date`, `responsible_id`, `commentary`, `status` (черновик или проведён),
  `was_cancelled`, `date_status`, `status_by`, `created_by`, `modified_by`, `created_at`,
  `updated_at`.
- **`store_document_items`** (`b_catalog_docs_element`): `id`, `doc_id` (каскад), `store_from`,
  `store_to`, `item_id`, `amount`, `purchasing_price`, `base_price`, `comment`.
- **Настройки** (таблица `options`):
  - `catalog.default_use_store_control` — «Складской учёт», по умолчанию нет;
  - `catalog.enable_reservation` — «Резервирование», по умолчанию да;
  - `catalog.allow_negative_amount` — показывать отрицательный остаток, по умолчанию нет;
  - `catalog.store_document_numbers_<тип>` — счётчики номеров;
  - `sale.product_reserve_condition` — `O`/`R`/`P`/`D`/`S`, по умолчанию `O`;
  - `sale.product_reserve_clear_period` — дни, по умолчанию 0 (не снимать);
  - `sale.allow_deduction_on_delivery` — отгружать при разрешении доставки, по умолчанию нет.

  Умолчания — из `default_option.php` Битрикса.

**Перевод существующих заказов.** Сейчас оформление сразу уменьшает `quantity` товара и `amount`
склада позиции, отмена возвращает (`orders.stock_deducted`). Миграция переводит такие заказы в
модель резервов: для неотменённых заказов со `stock_deducted` и неотгруженными отгрузками каждая
позиция учитываемого товара получает резерв:
- `quantity_reserved` товара += количество, `quantity` не меняется: оно уже уменьшено;
- для позиции со складом: `amount` склада += количество (физически товар ещё на складе),
  `quantity_reserved` склада += количество;
- срок резерва — без снятия.

Заказы с отгруженными отгрузками считаются списанными и не меняются. Поле `stock_deducted` после
миграции больше не пишется (остаётся для истории).

## Документы

Типы как в коробочной админке Битрикса:

| Тип | Название | Склады строки | Проведение | Отмена проведения |
|---|---|---|---|---|
| A | Приходная накладная | получатель | `amount` получателя +; закупочная цена товара; базовая цена, если в строке задана цена продажи | `amount` получателя − |
| S | Оприходование | получатель | как приход, без поставщика | как приход |
| M | Перемещение | источник и получатель | источник −, получатель + | источник +, получатель − |
| R | Возврат | получатель | `amount` получателя + | `amount` получателя − |
| D | Списание | источник | `amount` источника − | `amount` источника + |

**Название** документа — «<Тип> #<N>», как в Битриксе («Приходная накладная #2175»). N — следующее
значение счётчика `store_document_numbers_<тип>`.

**Проведение** (`conductDocument`). Одна транзакция, строки остатков блокируются. Сначала
проверяются все действия (`canExecute`), потом выполняются (`execute`). Проверки и тексты ошибок —
как в Битриксе:
- документ существует и указанного типа;
- в документе есть строки;
- у прихода указан поставщик;
- каждый товар существует; его тип — простой товар или торговое предложение;
- количество в каждой строке больше нуля;
- нужные склады строки указаны, существуют и активны, с отдельными текстами для прихода,
  оприходования и перемещения;
- у перемещения источник ≠ получатель;
- после уменьшения `amount` склада не < 0. Иначе — «недостаточно товара на складе», если у
  товара не включено «можно покупать при отсутствии».

Затем:
- доступное количество каждого товара пересчитывается по инварианту;
- статус становится «проведён», записываются `date_status` и `status_by`.

**Цены при приходе и оприходовании** (`UpdateProductPricesAction`):
- **закупочная цена:** записывается в `purchasing_price` в валюте документа; 0 очищает поле;
- **базовая цена:** записывается, если в строке задана цена продажи — обновляется первая цена
  базового типа или создаётся новая. Товар с диапазонами цен базового типа не трогается
  (`isExistPriceRanges`).

**Отмена проведения** (`cancellationDocument`):
- обратные движения с теми же проверками склада и минуса. Например, отменить приход нельзя, если
  остаток стал бы отрицательным;
- статус становится «черновик», `was_cancelled` = да;
- цены не откатываются.

**Правила:**
- черновик правится и удаляется;
- проведённый документ не правится и не удаляется — сначала отмена;
- без складского учёта раздел документов скрыт, проведение и отмена возвращают ошибку;
- со складским учётом поля остатков в карточке товара только для чтения.

## Резервы

**Когда ставится и снимается резерв.** Условие — `sale.product_reserve_condition`, поведение
как в `Sale\Order`:

| Условие | Ставится | Снимается |
|---|---|---|
| O — при оформлении | оформление заказа | — |
| R — при частичной оплате | появилась оплаченная оплата | оплаченных оплат не осталось |
| P — при полной оплате | заказ стал полностью оплачен | заказ перестал быть полностью оплачен |
| D — при разрешении доставки | у отгрузки разрешена доставка | разрешение снято, отгрузка не отгружена |
| S — при отгрузке | в момент отгрузки, перед списанием | — |

Во всех условиях резерв снимается при отмене заказа и при отгрузке (переходит в списание). Если
`catalog.enable_reservation` выключено, резервов нет.

**Склад резерва:**
- со складским учётом — склад позиции; если его нет, склад по умолчанию; если нет и такого,
  резерв ставится без склада;
- без складского учёта — без склада.

**Частичный резерв.** Резервируется не больше доступного. На недостающее в историю заказа пишется
предупреждение «Не удалось зарезервировать <N> шт. товара „<название>“». Заказ не падает. Проверка
наличия при оформлении остаётся как сейчас.

**Правка позиций** в админке или из 1С пересчитывает резервы по разнице. Удаление позиции снимает
её резерв.

**Срок и автоснятие:**
- резерв ставится с `date_reserve_end` = сегодня + `product_reserve_clear_period` дней;
- фоновая задача (как `currency::auto::spawn`) раз в час снимает резервы с `date_reserve_end` ≤
  сейчас, `quantity` > 0, у неоплаченных и неотменённых заказов, по 100 за проход
  (`RECORD_LIMIT`);
- при периоде 0 автоснятия нет.

**Ручные действия** в карточке заказа: «Снять резерв» и «Зарезервировать» — для позиции или для
всего заказа.

## Отгрузка

«Отгружено» (`shipments.deducted`) ставится и снимается в админке заказа и из 1С. При
`sale.allow_deduction_on_delivery` отгрузка ставится и при разрешении доставки
(`needShipOnAllowDelivery`).

**Склад списания позиции:**
1. склад из `shipment_item_stores`;
2. иначе склад позиции корзины;
3. иначе единственный склад, где у товара `amount` > 0 (`getAutoShipStoreData`); выбранный
   склад записывается в `shipment_item_stores`;
4. иначе ошибка «Не выбран склад для товара „<название>“» (`DDCT_DEDUCTION_STORE_ERROR`).

Шаги 1–4 — только со складским учётом.

**Списание** (`shipQuantityWithStoreControl` / `shipQuantityWithoutStoreControl`):
- **со складским учётом:**
  - `amount` склада − количество; если на складе меньше — ошибка
    `DDCT_DEDUCTION_QUANTITY_STORE_ERROR`;
  - резерв позиции снимается: резерв склада и товара уменьшаются;
  - если резерва было меньше количества, на разницу уменьшается доступное количество;
  - если не хватает и доступного — ошибка `DDCT_DEDUCTION_NOT_ENOUGHT_QUANTITY_PRODUCT`;
- **без складского учёта:**
  - сначала уменьшается резерв, потом доступное количество;
  - если суммы не хватает и товар без «можно покупать при отсутствии» — ошибка
    `DDCT_DEDUCTION_QUANTITY_ERROR`.

Ошибка любой позиции отменяет отгрузку целиком: флажок не ставится, остатки не меняются.

**Снятие «Отгружено»:**
- товар возвращается на те же склады;
- резерв восстанавливается, если заказ не отменён и условие резерва выполнено, иначе
  возвращается в доступное количество.

**Отмена заказа** с отгруженной отгрузкой запрещена: «Нельзя отменить заказ с отгруженными
отгрузками» (`SALE_ORDER_CANCEL_SHIPMENT_EXIST_SHIPPED`).

## Обмен с 1С

- **Остатки складов** из `offers.xml` пишутся в `amount`.
- **Доступное** = общее количество из 1С − `quantity_reserved` товара.
- **Отгрузка** с признаком проведения из 1С ставит «Отгружено» по правилам раздела «Отгрузка».
  Если списание не удалось, документ отгрузки не применяется, ошибка уходит в журнал обмена.

## Админка

Раздел «Магазин → Склады»:
- **Документы:**
  - список с фильтрами по типу, статусу, складу, поставщику и дате; колонки «номер», «тип»,
    «дата», «сумма», «статус»;
  - форма: шапка по типу, строки с поиском товара по названию, коду и артикулу;
  - кнопки «Сохранить», «Провести», «Отменить проведение», «Удалить»;
  - ошибки проведения — списком; документ остаётся черновиком.
- **Поставщики:** список и форма; поставщика, указанного в документах, удалить нельзя.
- **Остатки:**
  - таблица «товар × склад»: остаток, резерв, доступно; фильтр по складу и разделу;
  - по товару — его резервы с заказами и сроками.
- **Склады:** в форму добавлены «по умолчанию», «пункт выдачи», «отгрузочный склад».

**Карточка заказа:**
- колонка «резерв» у позиций;
- склад у позиций отгрузки;
- флажок «Отгружено»;
- «Снять резерв» и «Зарезервировать».

**Настройки:**
- каталог — «Складской учёт», «Резервирование», «Показывать отрицательный остаток»;
- магазин — «Условие резерва», «Срок снятия резерва (дней)», «Отгружать при разрешении доставки».

**Карточка товара** со складским учётом: остатки только для чтения, подсказка «меняются
документами»; закупочная цена.

## API для витрины

- **Остаток по складам** в bxapi и `/api/v1` — `amount`, как `catalog.store.amount` в Битриксе.
- **Количество и доступность товара** — `quantity`, уже за вычетом резервов, как
  `CATALOG_QUANTITY`.
- **Новых полей нет.**

Намеренное изменение: оформление заказа больше не уменьшает остаток склада позиции. Физически
товар ещё на складе, уменьшается только доступное количество (резерв), как в Битриксе. Остаток
склада в ответах после оформления заказа поэтому остаётся прежним до отгрузки. Регрессия
сравнивает ответы на одинаковом состоянии базы, без нового заказа между запросами.

## Перенос из Битрикса

`cms import-bitrix` дополнительно переносит:
- **`b_catalog_store`:** `IS_DEFAULT`, `ISSUING_CENTER`, `SHIPPING_CENTER`;
- **`b_catalog_store_product`:** `QUANTITY_RESERVED`;
- **`b_catalog_product`:** `QUANTITY_RESERVED`, `PURCHASING_PRICE`, `PURCHASING_CURRENCY`;
- **`b_sale_basket_reservation`** (к позициям перенесённых заказов) и
  **`b_sale_basket_reservation_history`**;
- **`b_sale_store_barcode`** → `shipment_item_stores`;
- **`b_catalog_contractor`**;
- **`b_catalog_store_docs`** и **`b_catalog_docs_element`** — с сохранением ID, номеров, статусов;
- **`b_option`:** `catalog.default_use_store_control`, `enable_reservation`,
  `allow_negative_amount`, `store_document_numbers_*`; `sale.product_reserve_condition`,
  `product_reserve_clear_period`, `allow_deduction_on_delivery`.

Правила:
- Остатки переносятся как есть, из документов не пересчитываются: 1С меняет их мимо документов.
- Строки с несуществующим товаром, складом или позицией заказа пропускаются с предупреждением в
  лог.
- Документы типов вне 5а (`U`, `I`, `W`) пропускаются с предупреждением.
- Повторный перенос заменяет документы, поставщиков и резервы целиком.

## Проверка

- **Модульные тесты:**
  - план движений документа для каждого типа, проведение и отмена;
  - выбор склада списания (шаги 1–4);
  - списание со складским учётом и без: резерв ≥, < количества, нехватка;
  - частичный резерв.
- **`sqlx::test`:**
  - проведение и отмена всех пяти типов;
  - проверки: нет строк, нет поставщика у прихода, неактивный склад, источник = получатель,
    минус, минус при «можно покупать при отсутствии»;
  - запрет правки и удаления проведённого;
  - закупочная и базовая цена при приходе; товар с диапазонами цен;
  - нумерация;
  - пять условий резерва, каждое — ставится и снимается;
  - резерв на склад по умолчанию;
  - правка позиций и удаление позиции;
  - автоснятие: срок, оплаченный заказ не трогается, период 0, лимит 100;
  - отгрузка и снятие отгрузки; запрет отмены отгруженного заказа;
  - `allow_deduction_on_delivery`;
  - обмен с 1С: доступно = 1С − резерв; отгрузка из 1С с ошибкой списания;
  - миграция существующих заказов;
  - перенос;
  - админка: только чтение остатков при учёте, раздел документов без учёта скрыт.
- **Сквозная проверка** на копии основной базы с переносом трансопта — по списку из «Цели».
- **Регрессия** на основной базе со складским учётом выключенным: bxapi и `/api/v1` байт в байт.
- **Локальный Битрикс:** запросы с побочными эффектами не отправляются.
