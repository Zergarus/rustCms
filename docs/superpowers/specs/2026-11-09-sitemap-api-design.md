# SEO: sitemap-эндпоинты

**Ревизия 2 (2026-11-09).** CMS — продукт для разных проектов, поэтому раскладка
«тип → коллекция → адрес» не может быть константой в коде: она настраивается в
админке и хранится в БД, по образцу битриксового модуля `seo` (`b_seo_sitemap` +
`b_seo_sitemap_iblock`). Фронт не трогаем: контракт ответов остаётся тем же, что
отдаёт живой Битрикс.

## Как это устроено в Битриксе и что переносим

| Битрикс | У нас |
|---|---|
| `b_seo_sitemap` (ACTIVE, NAME, SETTINGS) | `seo_sitemap` (active, name — тип в API, settings) |
| `b_seo_sitemap_iblock` (SITEMAP_ID, IBLOCK_ID) | `seo_sitemap_collection` (sitemap_id, collection_id) |
| `DETAIL_PAGE_URL` инфоблока | `detail_page_url` коллекции (уже импортируется) |
| Настройка «разделы/элементы» | `settings.include`: `items` \| `sections` |
| Имена файлов, dir, changefreq, priority | не переносим: XML и имена файлов собирает фронт |

`settings` — JSONB: `{"include": "items", "path_template": ""}`. Пустой
`path_template` означает «взять шаблон коллекции» (`detail_page_url` для записей,
`section_page_url` для разделов). Свой шаблон нужен там, где адрес витрины не
совпадает с шаблоном инфоблока (у ТрансОпта товары живут на `/product/{CODE|ID}/`,
а не в `/catalog/…/`).

## Контракт API (не меняется)

`GET /api/v1/seo/sitemap` → `{"status":"success","data":{"items":[{"type","count","lastmod"}]},"errors":[]}`

`GET /api/v1/seo/sitemap/{type}` → `{"status":"success","data":{"type","items":[{"path","lastmod"}]},"errors":[]}`

`lastmod` — RFC3339 `+00:00`, `null` в индексе при нуле записей. Неизвестный или
выключенный тип — 404 `{"error":"not_found",…}`. Порядок типов — `sort, id`.
Записи типа — по коллекциям в порядке `collection_id`, внутри — по id.

## Модель

`migrations/0030_seo_sitemap.sql`:

- `seo_sitemap`: `id`, `created_at`, `updated_at`, `active` (bool), `name`
  (уникальный тип в API, он же сегмент URL), `path_template` (по умолчанию `''`),
  `include` (`items` \| `sections`, по умолчанию `items`), `sort`.
- `seo_sitemap_collection`: `sitemap_id`, `collection_id`, оба `ON DELETE CASCADE`,
  первичный ключ по паре.

Правила видимости — как у публичного API: коллекция с `api_enabled`, запись
`active` и с наступившей датой публикации; разделы — `active`. Тип может
включать несколько коллекций: `count` — сумма, `lastmod` — максимум по ним.

Путь: шаблон из `seo_sitemap.path_template`, иначе шаблон коллекции; подстановки
битриксовые (`#SITE_DIR#`, `#SECTION_CODE_PATH#`, `#SECTION_CODE#`, `#ELEMENT_ID#`,
`#ELEMENT_CODE#`, `#ID#`, `#CODE#`) плюс `#ELEMENT_CODE_OR_ID#` — код в нижнем
регистре, при пустом коде id. Готовый путь приводится к каноническому виду:
нижний регистр, один слэш на конце.

## Админка

Страница «SEO → Sitemap» (`/admin/seo/sitemap`): список типов и форма
создания/правки — имя типа, активность, сортировка, коллекции (мультивыбор),
что включать (записи/разделы), шаблон пути. Права — `collections.manage`, как у
редактора SEO. Удаление типа убирает его из API; конфигурация пустая — индекс
отдаёт пустой список, фронт соберёт карту только из статических страниц.

Начальных данных в миграции нет: каждый проект настраивает свои типы сам.
Локальная база ТрансОпта заполняется вручную для сверки с Битриксом.

## Что уже сделано и остаётся

Эндпоинты, контракт, правила видимости и тесты — готовы; таблица типов
переезжает из констант в БД, добавляется админка. `catalog` у ТрансОпта
остаётся ненастроенным: slug семейств живёт в проектном коде и в CMS его нет.

## Проверка

`cargo test` — 1140 passed. Тесты `src/sitemap_tests.rs`: конфигурация типов
(порядок `sort, id`, счётчики по нескольким коллекциям, пустой индекс без
конфигурации), пути (код/id, нижний регистр, разделы через
`#SECTION_CODE_PATH#`), 404 для выключенного и неизвестного типа, CRUD в админке
с правами `collections.manage`, рендер и нормализация адресов.
`clippy -D warnings`, `fmt --check`, `diff --check` — успешно.

Сверка с Битриксом на копии CMS (:3010) и локальной базе ТрансОпта: пять типов
заведены в БД, счётчики 4330 / 0 / 143 / 421 / 0, пути `products` и `news`
совпадают посимвольно. `lastmod` на 3 часа меньше битриксового — импорт сохранил
локальное время как UTC; вне объёма задачи.

Отличие от Битрикса сознательное: имена файлов, dir, `changefreq` и `priority` не
храним — XML и разбивку на файлы собирает витрина.
