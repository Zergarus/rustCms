# Готовность CMS к замене Битрикс:Бизнес без CRM

Дата: 2026-11-13. Оценка по состоянию `main` (`be47c7b`), без изменений кода.

## Границы оценки

Сравниваем с **Битрикс:Бизнес без CRM-блока**: контент, инфоблоки, магазин,
заказы, оплата, доставка, скидки, формы, SEO, почта, пользователи, 1С,
файлы, админка. CRM, задачи, календарь, телефония и почтовый клиент в скоуп
не входят — это отдельный продукт. Синхронизация с Битрикс24 через вебхуки
пока не реализована; архитектурно её можно добавить маршрутами проекта
(`Project.routes`) + очередью, но это будущая задача.

## Короткий ответ

| Вопрос | Ответ |
|---|---|
| Готово к презентации тимлиду/руководителю как замена контентной и магазинной части Битрикс:Бизнес? | **Да, с оговорками ниже.** Это headless CMS + e-commerce ядро с bxapi-совместимым API, а не весь Битрикс. |
| Готово к пилотному production-проекту без CRM? | **Условно да**, после P0-чеклиста: капча/антибот, бэкапы, один инстанс, проверка платежей и 1С на живых данных. |
| Полная замена Битрикс:Бизнес без CRM? | **Почти по функциям TransOpt, но не как универсальный продукт.** Не хватает рассылок/маркетинга, мультисайта, Bitrix REST/экосистемы, антибота и части платёжных обработчиков. |
| Готово как «одна CMS для запуска разных проектов»? | **Да, по одной установке на проект.** Мультисайтовости/мультитенантности нет: проект компилируется в бинарник (`project/mod.rs`), одна установка — один сайт. |

## Что реально готово

### Контент и админка

- Коллекции, разделы произвольной глубины, поля всех основных типов, включая
  блочный редактор (`blocks`), множественные значения, файлы, привязки.
- Версии записей, журнал действий, поиск, SEO-метаданные, sitemap, импорт из
  Битрикса, экспорт JSON/CSV.
- Админка на MiniJinja+HTMX: списки, фильтры, сохранённые виды, вкладки,
  массовые действия, права групп и коллекций.
- SQL-консоль, обозреватель таблиц с правкой/DDL и Rust-скрипты — только
  супер-администраторам (`ADMIN_TOOLS_ENABLED`).

### Магазин

- Каталог, типы цен, валюты и курсы, склады, остатки, резервы, партии,
  штрихкоды, складские документы, себестоимость.
- Заказы, статусы, оплата, доставка, плательщики, корзины, скидки и купоны,
  НДС, возвраты, повтор заказа.
- Платёжные системы: настройки обработчика и секретов в админке; сейчас
  поддержан обработчик ЮKassa, остальные подключаются кодом проекта.
- Обмен с 1С: каталог и заказы, хуки проекта.

### API и интеграция с фронтом

- bxapi-совместимый слой (`/api/v1/**`): каталог, корзина, оформление,
  оплата, профиль, авторизация, формы, поиск, навигация, location.
- Собственный публичный API `/api/v1/iblocks*`, OpenAPI, health, метрики.
- Проектные расширения: декораторы ответов, формы и их проверки, платёжные
  провайдеры, хуки 1С, условия скидок, свои маршруты.
- 1360 автоматических тестов (4 ignored), clippy/fmt чистые; тесты bxapi
  покрывают основные сценарии фронта.

### Эксплуатация

- Dockerfile + prod-compose, nginx/systemd-примеры, healthcheck, миграции при
  старте, инструкции по установке, обновлению и бэкапам.
- Импорт из Битрикса одной командой, перенос файлов `/upload/*`.

## Чего нет или недостаточно

### 1. Функциональные пробелы в скоупе «Бизнес без CRM»

- **Рассылки и маркетинг:** есть шаблоны писем и события, но нет подписчиков,
  сегментов, кампаний и статистики рассылок.
- **Платёжные обработчики:** в админке только ЮKassa; СБП, эквайринг,
  Робокасса и другие подключаются кодом проекта.
- **Доставка:** службы и склады настраиваются вручную, интеграций с API
  перевозчиков (СДЭК, Почта, Boxberry) нет.
- **Налоги:** одна ставка НДС на магазин, без налоговых групп (TD-056).
- **Мультисайт/домены:** нет; один проект — одна установка.
- **Bitrix REST и маркетплейс приложений:** совместим только bxapi-контракт
  фронта, а не весь REST API и экосистема модулей Битрикса.
- **Обновления/бэкапы/антибот:** снаружи, не встроены в продукт.

Это не мешает запуску проекта масштаба TransOpt, но мешает назвать CMS
универсальной заменой любого Битрикс:Бизнес «из коробки».

### 2. Мультипроектность

- `project/mod.rs` компилируется в бинарник через `build.rs`; одна установка —
  один проект. Для десяти сайтов нужно десять инстансов (или отдельная
  платформа), а не одна админка с доменами.
- Нет мультисайтовости, общих пользователей между сайтами, переключателя
  проектов. Для агентства это означает отдельный деплой и базу на проект.
- Плюс: граница «ядро/проект» проведена аккуратно, проектный код не попадает в
  `src/`.

### 3. Безопасность и антиабьюз

- Капча на регистрации/восстановлении **не реализована**: `smartCaptchaToken`
  принимается и игнорируется (TD-010). До публичного запуска нужен антибот.
- Rate-limit и лимит попыток входа — в памяти инстанса (TD-014, TD-051): при
  нескольких инстансах/прокси бюджет не общий.
- Журнал покрывает не все изменения (TD-038), нет очистки `audit_log` (TD-039).
- Секреты платёжных систем хранятся в БД без шифрования (TD-067); это
  осознанно, но нужно понимать при аудите.
- Инструменты супер-админа дают выполнение SQL и произвольного Rust без
  песочницы (TD-059): для production это отдельный риск, включать осознанно.

### 4. Эксплуатационная зрелость

- Нет CI-пайплайна в репозитории: тесты/clippy не проверяются автоматически
  на каждый push; релиз собирается вручную.
- Бэкапы описаны, но не автоматизированы; нет проверки восстановления.
- `/metrics` открыт без авторизации, метрики в памяти без гистограмм и
  маршрутов (TD-055); трейсинга нет.
- Очередь писем и фоновые задачи рассчитаны на один инстанс: при
  масштабировании возможны дубли (TD-053).
- Миграции forward-only; откат — только восстановление бэкапа.
- Нет нагрузочных тестов и формального SLA; текущая база (~23k записей)
  небольшая, поведение на миллионах записей не проверялось.

### 5. Платежи, 1С и налоги

- В админке секреты только для ЮKassa; другие провайдеры — код проекта.
- Возврат фиксируется в CMS, но не проводится у провайдера и не возвращает
  товар на склад (TD-057).
- Обмен заказами с 1С не проверялся на живой 1С (README/parity).
- Одна ставка НДС на магазин, без налоговых групп (TD-056).

### 6. Мелочи паритета

- Капча, повторная отправка подтверждения почты, уникальность e-mail для
  импортированных аккаунтов (TD-011/012/013).
- Проектные сценарии (сотрудники, отзывы, водяные знаки, массовая правка цен,
  уведомления о низком остатке) не входят в ядро — это расширения проекта.

## Что показать на презентации

1. Перенос данных из Битрикса и открытие знакомого фронта без правок API.
2. Коллекции, поля, блоки, версии, SEO и sitemap в админке.
3. Полный цикл заказа: корзина → оформление → оплата → статус → повтор.
4. Импорт/обмен 1С и складские документы.
5. Инструменты супер-админа (SQL/таблицы/Rust) — как аналог Bitrix-инструментов.
6. Честно обозначить рамку: «ядро CMS + магазин», а не CRM-платформа.

## P0 перед пилотным production

- [ ] Антибот на регистрации/восстановлении (капча или эквивалент).
- [ ] Общий rate-limit/лимит попыток (БД/Redis) либо зафиксировать один инстанс.
- [ ] Автоматические бэкапы БД и `UPLOAD_DIR` + проверка восстановления.
- [ ] CI: `cargo test`, clippy, сборка Docker на каждый push.
- [ ] Проверить платежи и вебхуки на реальном провайдере, возвраты — регламент.
- [ ] Проверить обмен с живой 1С на тестовой базе.
- [ ] Решить судьбу `/metrics` (закрыть или ограничить) и включить трейсинг.
- [ ] Прогнать нагрузочный сценарий каталога/поиска/заказа на объёме, близком
      к production.

## Вывод

Если сравнивать с **Битрикс:Бизнес без CRM**, проект закрывает контент,
каталог, заказы, оплату, склад, скидки, формы, SEO, почту, пользователей и 1С
на уровне, достаточном для проекта масштаба TransOpt. Его **можно показывать**
как рабочую CMS/интернет-магазин и кандидата на пилот.

Но как «универсальная замена Битрикс:Бизнес для любого проекта» он пока не
готов: нет рассылок/маркетинга, мультисайта, Bitrix REST и экосистемы,
обработчиков большинства платёжных систем и API доставок; эксплуатационная
обвязка (CI, антибот, общие лимиты, бэкапы, нагрузка) не достигла уровня
«поставил и забыл». Для одного проекта — да, после P0. Для потока проектов —
по одной установке на каждый плюс автоматизация деплоя.
