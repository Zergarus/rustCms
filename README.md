# CMS на Rust

Headless CMS по мотивам 1С-Битрикс: админ-панель для управления контентом, публичный JSON API для фронтенда и API, совместимое с модулем `mediagroup.bxapi` — фронт, написанный под Битрикс, работает с CMS без правок. Данные переносятся из базы Битрикса одной командой.

**Стек:** Axum 0.8 · PostgreSQL + SQLx 0.9 · MiniJinja (шаблоны админки) · HTMX · argon2.

## Запуск

```bash
docker compose up -d                  # PostgreSQL
cp .env.example .env
cargo run -- create-admin admin       # создать администратора (спросит пароль)
cargo run                             # http://127.0.0.1:3000/admin
```

Миграции применяются автоматически при старте. Отдельно: `cargo run -- migrate`.

Переменные окружения — в `.env.example`.

## Коллекции

Коллекция — настраиваемый тип контента (новости, статьи, товары), аналог инфоблока Битрикса. Словарь:

| Битрикс | В CMS | В коде и БД |
|---|---|---|
| Инфоблок | Коллекция | `collections` |
| Элемент | Запись | `collection_items` |
| Раздел | Раздел | `collection_sections` |
| Свойство | Поле | `collection_fields` |
| Значение списка | Вариант | `collection_field_options` |

Внешние API (наш `/api/v1/iblocks` и bxapi) сохраняют имена Битрикса ради совместимости.

У коллекции есть:

- **разделы** — дерево произвольной глубины (код, внешний код, картинка, описание);
- **поля** — строка, текст, число, да/нет, дата, список (варианты с XML_ID), привязка к записи (можно ограничить коллекцией), файл; любое, кроме текста и да/нет, может быть множественным;
- **записи** — название, код, внешний код, раздел, активность, сортировка, анонс и детальный текст с картинками, дата публикации и значения полей (`field_values`, JSONB: одиночное — скаляр, множественное — массив; список хранит id варианта, привязка — id записи, файл — id файла).

Символьный код записи необязателен (уникален только непустой) и генерируется из названия транслитерацией. HL-блоков отдельно нет: справочник — обычная коллекция, а поле-справочник — привязка к записи (`user_type = directory`, связь по внешнему коду).

Торговый каталог (как модуль `catalog`): флаг «Торговый каталог» у коллекции включает у её записей вкладку с ценами по типам цен, остатками по складам и флагами «доступен для покупки», «учитывать количество», «покупка при нулевом остатке» (значение «по умолчанию» берётся из настроек каталога). Выключение флага прячет цены и остатки из API и делает товары недоступными для покупки, но данные сохраняются.

## Торговые предложения

Предложения (SKU) — записи коллекции предложений, привязанные к товару; аналог торговых предложений Битрикса.

- **Связь.** В карточке коллекции с «Торговым каталогом» — блок «Торговые предложения»: использовать существующую коллекцию или создать новую (`<код>_offers`). Связь — системное поле `cml2_link` (API: `cml2Link`), значение хранится в `collection_items.product_id`. Вкладка и генератор требуют права записи на обе коллекции.
- **Типы товара.** 1 простой, 3 с предложениями, 4 предложение, 6 — товар с предложениями, у которого их не осталось. Тип и доступность товара пересчитывают триггеры БД: появилось предложение — тип 3, все предложения удалены — тип 6.
- **Генератор.** Из карточки товара: сочетания значений полей с «Поле выбора предложения», общие цена, остатки по складам и вес. Новые предложения получают UUID в `xml_id`. За запуск — не больше 100 сочетаний; существующие сочетания пропускаются. Шаблон названия по умолчанию — `#PRODUCT_NAME# (#CODE1#, #CODE2#)`. Итог: «Создано N, пропущено M (уже есть)».
- **Поля предложения.** Флажки в форме поля: «Показывать в корзине» (`IN_BASKET`) и «Поле выбора предложения» (`OFFER_TREE`).
- **bxapi.**
  - `select`: `catalogType` (1, 3, 4, 6; `null` вне каталога). У товара типа 3 `catalogPrice` — самое дешёвое доступное предложение, а если доступных нет — самое дешёвое активное, с `"fromOffers": true`, `stocks` — сумма по складам активных предложений. Тип 6 или без активных предложений — `catalogPrice: []`, `stocks: []`.
  - `filter`: ключ `offers` без оператора — товары, у которых есть предложение под вложенный фильтр: `{"offers": {"volume": "4 л"}}`. Работает внутри `logic: OR` и в `hasElements`.
  - Предложения — обычная коллекция: `iblock/{apiCode}/element/list` с `filter cml2Link.element.id`.
- **Корзина и заказ.** Товары типа 3 и 6 в корзину не кладутся (`product_not_found`), как и предложения неактивного товара; проверка идёт при добавлении в корзину, в снимке корзины (`isAvailable`, `canCheckout`), при оформлении заказа и при правке заказа в админке. В позицию пишутся свойства полей «Показывать в корзине» предложения и товара, затем `PRODUCT.XML_ID` и `CATALOG.XML_ID`. Личный кабинет отдаёт `items[].properties` (все свойства, затем `STORE_ID`) и `items[].weight` (граммы). Карточка заказа в админке и письмо не показывают служебные `*.XML_ID`.
- **Импорт.** `cms import-bitrix` переносит коллекции предложений, связи `CML2_LINK`, типы и веса товаров (типы 2 и 5 становятся простыми), флаги `IN_BASKET` и `OFFER_TREE`.
- **Не входит:** единицы измерения, НДС и наценки; предложения в ответе товара (отдельный запрос по `cml2Link`); сортировка по цене «от».

## Перенос из Битрикса

```bash
cms import-bitrix 'mysql://user:pass@host:3306/db' --upload /path/to/site/upload [--replace] [--api-code 14=info]
```

Переносит инфоблоки, свойства, варианты списков, разделы, элементы со значениями свойств (хранение v1 и v2), HL-блоки (как инфоблоки), торговый каталог (цены, склады с реквизитами, остатки, валюты), пользователей (с полями профиля, UF-полями и фото), группы пользователей, местоположения модуля sale, настройки оформления заказа (статусы, типы плательщика, свойства заказа с вариантами и привязками к оплате и доставке, службы доставки со складами самовывоза, платёжные системы с ограничением по группам), почтовые шаблоны и нужные настройки ядра (`email_from`, `site_name`, `server_name`). Id инфоблоков, разделов, элементов, свойств и файлов сохраняются как в Битриксе. Пользователи входят со своими паролями: хеши Битрикса (`$6$…` и старый md5 с солью) проверяются и при входе заменяются на argon2. Инфоблоки становятся коллекциями, свойства — полями, элементы — записями. Повторный запуск с `--replace` заменяет коллекции; пользователи обновляются, а не дублируются. `--api-code` задаёт apiCode инфоблоку, у которого API_CODE в базе не заполнен.

## Обмен с 1С

Каталог обменивается с 1С по протоколу Битрикса: в настройках обмена 1С меняется только адрес сайта.

- **Адрес.** `/api/1c/exchange` (GET и POST; в настройках 1С указывается вместо адреса Битрикса); ответы — текст (`success`, `progress`, `failure`).
- **Право.** «Обмен с 1С» или суперадминистратор. `checkauth` — HTTP Basic, дальше сессия по cookie `CMS_1C_SID` (или параметру `sessid`). Сессия живёт 24 часа с последней активности; право и активность пользователя проверяются на каждом запросе.
- **Форматы.** CommerceML 3.1 (`groups`, `propertiesGoods`, `units`, `storages`, `priceLists`, `goods`, `prices`, `rests`) и классический 2.x (`import.xml` + `offers.xml`); кодировки UTF-8 и windows-1251.
- **Порядок.** `init` → `file` (тело пишется в каталог сессии частями, лимит `file_limit`, по умолчанию 200 МБ) → `import` (один файл за вызов, одна транзакция) → `deactivate` и `complete` — только после полной выгрузки. Zip распаковывается при импорте; обрезанный архив даёт `failure`, пока не докачан целиком. Повторный импорт того же файла в сессии даёт `success` без повторного применения. Если в сессии был неуспешный импорт, шаг деактивации пропускается (ответ `deactivate` сообщает об этом). `complete` всё равно закрывает сессию и, если `deactivate` не вызывался, сам выполняет деактивацию (после полной выгрузки).
- **Сопоставление** (по `xml_id` = `Ид` из 1С):
  - каталог или классификатор — в коллекцию по `Ид`; если такой нет и задана коллекция по умолчанию — в неё (даже если у неё уже есть свой `Ид`: он не перезаписывается, пустой заполняется `Ид` пакета), иначе создаётся новая. Коллекцией по умолчанию может быть только коллекция каталога, не предложений; группы — в дерево разделов. Раздел, который деактивировал администратор, обмен никогда не активирует снова; сортировка из пакета применяется только при полной выгрузке;
  - свойства — в поля: справочник → список с вариантами, строка, число, дата. Вид уже существующего поля не меняется;
  - системные поля `cml2_article`, `cml2_bar_code`, `cml2_manufacturer`, `cml2_traits`, `cml2_taxes`, `cml2_base_unit`, `cml2_pictures` (или существующее поле с `xml_id` `CML2_PICTURES`);
  - склады и типы цен создаются, если их нет; удалённый в 1С склад деактивируется, а пришедший снова без пометки — активируется;
  - товары — в записи: код транслитом по настройке, первая картинка — детальной и превью, вес в граммах. запись без пометки на удаление становится активной, даже если администратор её деактивировал (наличием товаров управляет 1С, как в Битриксе);
  - цены заменяются по каждому типу цен; остатки — по складам, `quantity` = сумма;
  - `товар#характеристика` — торговые предложения (при настройке «Использовать торговые предложения»); помеченное на удаление предложение деактивируется или удаляется по действию для записей;
  - файлы дедуплицируются по sha256: та же картинка при повторной отправке сохраняет свой файл.
- **Настройки** (админка, раздел «Обмен с 1С»): коллекция по умолчанию; действие для разделов и записей, которые не пришли в полной выгрузке или помечены на удаление (ничего / деактивировать / удалить); транслит кода при добавлении и при обновлении; торговые предложения; деактивация товаров без цены (только записи текущего пакета, получившая цену снова активна, а предложение — вместе со своим товаром); интервал шага (0 — без ограничения; хранится для совместимости с Битриксом, но CMS импортирует файл целиком за один вызов, поэтому на обмен не влияет); лимит файла в МБ (1–4096); использование zip. Страница показывает журнал последних 50 обменов.
- **Перенос из Битрикса** переносит XML_ID инфоблоков, свойств, складов и типов цен, а опции `catalog/1C_*` — в настройки обмена.
- **Безопасность.** Пути с `..`, абсолютные пути и ссылки в `filename` и в записях zip отклоняются; распакованный архив — не больше 2 ГБ и 100 000 записей. Картинка или файл, на который ссылается пакет и которого нет в пакете, не меняет значение поля.
- **Не входит:** выгрузка каталога в 1С, справочник единиц измерения, НДС.

### Заказы

Заказы обмениваются с 1С по протоколу компонента `sale.export.1c` Битрикса (`type=sale` на том же адресе): сайт отдаёт новые и изменённые заказы, 1С присылает изменения заказов, оплат и отгрузок, а при включённых настройках — новые заказы, оплаты и отгрузки.

- **Право.** «Обмен заказами с 1С» (`exchange.1c.sale`) или суперадминистратор; право «Обмен с 1С» его не даёт, и наоборот. Вход и сессия — как у каталога.
- **Порядок.** `checkauth` → `init` → `query` → `success` → `file` → `import`; `info` — в любой момент сессии.
  - `init`: `zip=yes|no` и `file_limit=<байты>`; если передан `version` — ещё `sessid=<токен>` и `version=2.09`. Без `version` работает старый протокол: `file` сразу загружает присланный файл (у архива — первый файл архива), а `query` выгружает все подходящие заказы без ограничения по интервалу.
  - `query`: XML заказов в `application/xml; charset=windows-1251` (символы вне кодировки — `?`). Без `success` следующий `query` отдаёт те же заказы снова.
  - `success`: подтверждает последнюю выгрузку сессии — выгруженные заказы больше не уходят, пока их не изменят на сайте; без `query` в сессии ответ `error`.
  - `import`: документы файла по шагам в пределах интервала (`progress`, затем `success` с итогом всего файла «Создано: … Обновлено: …» или текстами ошибок документов всех шагов построчно); повторный `import` того же файла в сессии — `success` без повторного применения.
  - `info`: справочники в XML (windows-1251) — статусы, активные платёжные системы с типом оплаты (наличные, безналичные, эквайринг), активные службы доставки.
  - `cmlVersion` от 2.10 (новая схема Битрикса) — `failure` «Схема обмена cmlVersion ≥ 2.10 не поддерживается» на `query` и `import`.
- **Версии схемы** — по `version` из `init` (запятая равна точке), без `version` — 2.05. Выше 2.05 — `НомерВерсии`, `Номер1С`, единица измерения с кодом (796 «шт» по умолчанию), типы контактов «Телефон рабочий» и «Электронная почта» (иначе «ТелефонРабочий» и «Почта»); от 2.10 за заказом идут документы оплат, отгрузок и удалённых отгрузок; от 3 — документы одного заказа в `<Контейнер>`.
- **Выгрузка.** Уходят заказы, изменённые на сайте после последнего подтверждённого `query`, кроме созданных в 1С и изменённых обменом; фильтры настроек: только оплаченные, только с разрешённой доставкой, начиная со статуса (неизвестный статус — без фильтра, с предупреждением в логе). Метка выгрузки не заходит за начало незавершённых транзакций и за заказ, документ которого не собрался (такой заказ пропускается с предупреждением в логе и уходит в следующих выгрузках). Документ заказа — как у `CSaleExport`: номер с префиксом, валюта с заменой, контрагент, товары (у предложения Ид `товар#характеристика`), доставка строкой-услугой `ORDER_DELIVERY`, склады отгрузки, реквизиты (оплата, доставка, отмена, статус, адрес, произвольные реквизиты соответствия и реквизиты модуля проекта). Ид контрагента берётся из `users.xml_id`; пустой при первой выгрузке заполняется по правилу Битрикса (`<id>#<логин>#<ФИО>`, первые 40 символов), у гостя — `<id заказа>#guest`.
- **Приём.** Каждый документ — своя транзакция (документы одного `Контейнер` — общая); ошибка одного документа не мешает остальным. Документ с `НомерВерсии` не новее сохранённого пропускается, поэтому повтор файла не создаёт дублей. Заказ ищется по `Номер` — как номер сайта (наш id, затем номер 1С `id_1c`, затем номер заказа `account_number`; с префиксом магазина — то же без префикса), затем `Ид` и `Номер1С` — только по номеру 1С; оплата и отгрузка — по своему id в заказе-основании, затем по Ид 1С.
  - заказ: номер и версия 1С, статус (при настройке «Менять статус из 1С», с историей и письмом), отмена и снятие отмены (с остатками), пометка удаления — отмена, состав (при «Обновлять количество в корзине»; оплаченный или отгруженный заказ по составу не правится — ошибка «заказ в финальном состоянии» в итоге, но статус и отмена применяются, а номер и версия 1С не пишутся, и документ придёт снова); новый заказ — с покупателем по контрагенту (по `users.xml_id`, иначе новый пользователь без пароля), типом плательщика по домену (юрлицо при непустом ИНН), свойствами по соответствию и отгрузкой службой по умолчанию;
  - оплата: оплачена (дата и номер документа из 1С), возврат, удаление неоплаченной, новая — платёжной системой по умолчанию для своего типа оплаты; `paid` заказа — все оплаты оплачены;
  - отгрузка: отгружена (номер и дата, трек), доставка разрешена, переход заказа в «Статус при отгрузке», удаление неотгруженной, новая — службой по умолчанию. Остатки при отгрузке не списываются повторно (списание — при оформлении заказа).
  - Изменения из обмена помечаются (`updated_1c`) и не возвращаются в 1С; любое изменение заказа на сайте (оформление, админка, оплата, отмена, ЮKassa) снимает пометку, и заказ снова уходит в выгрузку.
- **Настройки** (вкладка «Заказы» страницы «Обмен с 1С»; умолчания — как в Битриксе): выгружать только оплаченные (нет), только с разрешённой доставкой (нет), начиная со статуса (все), замена валюты и префикс номера (пусто), менять статус из 1С (нет), статус при отгрузке (не задан), обновлять количество в корзине, создавать новые заказы, оплаты, отгрузки и отгрузку для нового заказа (да), платёжные системы по умолчанию для наличных, безналичных, эквайринга и оплаченного заказа и служба доставки по умолчанию (не заданы). Интервал, лимит файла и zip — общие с каталогом.
- **Соответствие реквизитов** (аналог `b_sale_bizval` с потребителем «1C») — по типам плательщика: домен (физлицо или юрлицо), поля контрагента с кодами Битрикса `BUYER_PERSON_*` / `BUYER_COMPANY_*` и произвольные реквизиты `1C_REKV_<n>`; источник значения — свойство заказа, поле пользователя, поле заказа или константа. Поля без соответствия заполняются как в Битриксе: почта пользователя, имя плательщика, свойства-телефон, адрес и местоположение. После миграции 0018 у всех существующих типов плательщика домен «физлицо»: юрлицам задайте домен «юрлицо» здесь или повторите `cms import-bitrix` (переносит домены из `b_sale_bizval_persondomain`), иначе новые заказы юрлиц из 1С не создаются — ошибка «тип плательщика не найден».
- **Журнал** — общий с каталогом, с колонкой «тип» и счётчиками заказов, оплат и отгрузок. В карточке заказа админки — блок «1С» (номер и версия 1С, «изменён из 1С», «создан в 1С», номера, даты и трек оплат и отгрузок) и «Выгрузить XML для 1С» — документ заказа без побочных эффектов (метка выгрузки не двигается, Ид контрагента не сохраняется).
- **Перенос из Битрикса** переносит опции `sale/1C_*` в настройки обмена заказами, метку последней подтверждённой выгрузки, соответствие реквизитов `b_sale_bizval` (с подстановкой `COMMON`), домены типов плательщика (`b_sale_bizval_persondomain`) и `XML_ID` пользователей.
- **Модуль проекта**: `order_export_hook` (`OrderExportHook`) дописывает свои реквизиты в документ заказа, `order_import_hook` (`OrderImportHook`) разбирает документ из 1С по-своему после штатной записи, в той же транзакции (ошибка отменяет документ) — аналог событий обмена Битрикса.
- **Не входит:** новая схема обмена (`cmlVersion` ≥ 2.10, «Документы.Подчинённые»), обмен счетами Битрикс24/CRM, перенос самих заказов из Битрикса, маркировка, кассовые чеки, НДС в документе.

## Корзина

Аналог `b_sale_fuser`/`b_sale_basket` с контрактом раздела «Корзина» модуля bxapi: `GET /api/v1/cart`, `POST /api/v1/cart/items` (`{productId, quantity, storeId?}`), `cart/items/{id}/quantity` (`0` удаляет), `cart/items/{id}/store`, `cart/items/{id}/remove`, `cart/clear`; каждый ответ — полный снимок корзины (позиции с ценой, складами и остатками, итоги, `canCheckout`, `snapshot`).

- Корзина гостя хранится на сервере по cookie `CMS_BUYER` (создаётся при первом добавлении товара); при входе она объединяется с корзиной пользователя — одинаковый товар на одном складе складывается.
- Цена пересчитывается при каждом чтении (базовый тип цены, иначе первый по сортировке); количество ограничено остатком на выбранном складе или общим, если товар учитывает количество и не продаётся при нулевом остатке.
- Настройки сайта (аналог `bxapi.basket`) — `CartConfig` в модуле проекта: свойство артикула, свойства позиции (пути через точку, как в `select`), поля и UF-поля склада, режим подсчёта (штуки или позиции), обязательные свойства, ширина картинки.

## Заказы

Аналог модуля `sale` с контрактом раздела «Оформление заказа» модуля bxapi: `GET /api/v1/order/form` (типы плательщика, блоки свойств, доставки со складами самовывоза, платёжки, корзина, итоги), `POST /api/v1/order/summary`, `POST /api/v1/order/submit`.

- Оформляется вся корзина (со сверкой `basketSnapshot`) или её часть (`basketItems`) — фронт может сделать из одной корзины несколько заказов; оформленные позиции уходят из корзины.
- Свойство заказа с привязкой к платёжкам или доставкам участвует только при выбранных оплате и доставке; пустые email, телефон и ФИО вошедшего берутся из профиля.
- Остатки окончательно проверяются под блокировкой строк и списываются при оформлении (только у товаров с учётом количества): одновременные заказы не продают больше, чем есть. Отмена заказа возвращает остатки, снятие отмены и правка состава списывают разницу.
- Гость получает учётную запись: найденную по email, затем по телефону, или новую (без автоматического входа); цены и скидки заказа гостя — гостевые (без групп найденного пользователя), как в корзине и итогах, которые он видел. Если стоимость товаров заказа всё же разошлась с итогами, в ответе `submit` — `messages`.
- Письма — почтовые события `SALE_NEW_ORDER`, `SALE_STATUS_CHANGED_<статус>` (если у статуса включено уведомление), `SALE_ORDER_CANCEL`, `SALE_ORDER_PAID` с полями как в Битриксе.
- Настройки сайта (аналог `bxapi.order`) — `OrderConfig` в модуле проекта: белые списки типов плательщика, доставок и платёжек, скрытые свойства, порядок блоков, группы новых покупателей, тип платёжки для фронта, фильтр доставок по составу корзины (`DeliveryFilter`).

## Личный кабинет

Контракт раздела «Личный кабинет» модуля bxapi; все эндпоинты — только для вошедших (без сессии — 401 `unauthorized`).

- `GET /api/v1/profile` — поля профиля, список редактируемых (`editable`) и число заказов (`ordersCount`); аватар — путём `/upload/...`.
- `POST /api/v1/profile` — JSON или multipart: меняются только редактируемые поля, аватар (`personalPhoto`, только картинки; `personalPhotoDelete=Y` — убрать), смена пароля (`password` + `passwordRepeat`, не короче 6 символов), проверка email на формат и занятость. Ошибки — 400 `profile_update_failed` со словарём полей.
- `GET /api/v1/profile/orders?limit&offset` и `GET /api/v1/profile/orders/{id}` — заказы пользователя, новые первыми: статус, отгрузки (трек-номер, склады самовывоза службы), платежи, позиции (склад, картинка товара), свойства заказа объектом с ключами в camelCase. Файловые свойства (накладная, счёт, УПД) — объектами файла как в Битриксе, множественные — массивом. Чужой заказ — 404 `order_not_found`.
- Настройки сайта (аналог `bxapi.profile`) — `ProfileConfig` в модуле проекта: поля профиля и редактируемые поля (имена `b_user`, `UF_*`), `ordersCount`, размер страницы заказов, формат даты.

## Магазин в админке

Раздел «Магазин»:

- «Работа с заказами»: список заказов с фильтрами (номер, статус, период, покупатель, оплата, отмена), карточка — смена статуса с историей, оплата, отмена с причиной, свойства и комментарий менеджера, правка состава (количество, склад, своя цена, удаление и добавление товаров, доставка и оплата; одновременная правка двумя менеджерами отклоняется), документы заказа (загрузка и удаление файлов в файловые свойства — видны покупателю в личном кабинете), трек-номер и разрешение доставки.

## Скидки

Аналог правил работы с корзиной модуля `sale` Битрикса (`Sale\DiscountBase`): скидки и наценки считаются так же, как в Битриксе, и видны в корзине, итогах формы, заказе, письмах, истории заказов, админке и выгрузке в 1С. Код — `src/discount/`: движок — чистая функция `discount::calculate(rules, &Context)` без БД.

- **Правило** (`discounts`): название, активность и период, приоритет (1), сортировка (100), «прекратить дальнейшее применение» (`last_discount`), «прекратить применение на текущем уровне приоритетов» (`last_level_discount`), «только по купону» (`use_coupons`), группы пользователей (`discount_groups`; без групп — для всех), деревья `conditions` и `actions`.
- **Деревья** — JSON в формате Битрикса `{ "CLASS_ID", "DATA", "CHILDREN" }`, ключи и значения `DATA` дословно (`All` `AND`/`OR`, `True` `True`/`False`, `logic` `Equal`/`Not`/`Great`/`Less`/`EqGr`/`EqLs`/`Contain`/`NotCont`, `value`); ссылки — наши id (коллекции, поля, записи, разделы, варианты списков, группы, платёжки, доставки, типы плательщика).
- **Условия:** `CondGroup`; корзина — `CondBsktCntGroup`, `CondBsktAmtGroup`, `CondBsktAmtBaseGroup`, `CondBsktProductGroup`, `CondBsktRowGroup`, `CondBsktSubGroup`, поля строки `CondBsktFldProduct|Name|Price|Quantity|Summ|Weight`, `CondBsktAppliedDiscount`; товар строки (у предложения — и его родитель) — `CondIBElement`, `CondIBIBlock`, `CondIBSection`, `CondIBXmlID`, `CondIBName`, `CondIBCode`, `CondIBProp:<коллекция>:<поле>`, `CondCatQuantity`, `CondCatWeight`; заказ — `CondSaleOrderSumm`, `CondSaleOrderWeight`, `CondSalePersonType`, `CondSalePaySystem`, `CondSaleDelivery`, `CondSaleCmnDayOfWeek`. `Contain`/`NotCont` — с учётом регистра, как `mb_strpos`.
- **Действия:** `ActSaleBsktGrp` — позиции под вложенными условиями, `Type` `Discount` (скидка) / `Extra` (наценка) / `Closeout` (установить цену), `Unit` `Perc` / `CurEach` (на единицу) / `CurAll` (сумма, распределённая пропорционально стоимости позиций), `Max` — не больше на единицу; `ActSaleSubGrp` — подгруппа действий; `ActSaleDelivery` — доставка, `Type` `Discount` / `DiscountZero` / `Extra`, `Unit` `Perc` / `Cur`.
- **Неизвестный класс** (например, `ActSaleGift` из Битрикса или класс проекта без `discount_condition_hook`) записывается в `unsupported`: правило сохраняется, но не применяется, админка показывает предупреждение.
- **Накопительные скидки.** Условие `CondCumulativeGroup` (`logic`, порог `Value`, один вложенный `Period` с `ValueStart`/`ValueEnd` в unix-секундах или `PeriodRelative` с `Value` и `TypeRelativePeriod` `D`/`M`/`Y`; без периода — за всё время) и действие `CumulativeAction` (`ranges[{sum, value, type}]`, `type` `P` — процент, `F` — сумма на единицу; `type_sum_period` `all_time`/`interval`/`relative`, `sum_period_data`, `apply_if_more_profitable`, вложенные условия позиции). Применяется последний порог, который покрыт накопленной суммой; «только если выгоднее» считает скидку от базовой цены и заменяет прежние скидки позиции, если итог ниже. Пресет «Накопительная скидка» в списке правил собирает такое правило формой (пороги, период, «только если выгоднее», «пропускать позиции со скидкой»). **Накопленная сумма** — `orders.price` (с доставкой) оплаченных неотменённых заказов покупателя за период, в валюте первого заказа периода (курсов валют нет, заказы в других валютах пропускаются); у гостя — 0. Движок остаётся чистой функцией: суммы для нужных периодов считаются одним запросом перед расчётом, без накопительных правил запросов нет. В цену со скидкой каталога такие правила не входят.
- **Подарки.** Действие `GiftCondGroup` с одним вложенным `GifterCondIBElement` (`Value` — id записей) или `GifterCondIBSection` (`Value` — id раздела), `Type` `one` (первая подходящая позиция) / `all`. Бесплатной становится позиция количеством ровно 1 с ценой больше нуля и без `custom_price` (у предложения подходит и подарок, указанный по родителю); скидка равна цене до действия. Подарки в корзину CMS не кладёт и не убирает. Доступные подарки: bxapi `basket` отдаёт `gifts: [{ruleId, type, productIds}]` (только при активных правилах с подарками), `GET /catalog/gifts?productId=` — подарки, которые появятся с этим товаром в корзине.
- **Округление цен** (`catalog_rounding`, как `b_catalog_rounding`): правила типа цены с порогом, способом (`math`/`up`/`down`) и точностью (пресеты Битрикса от 0.0001 до 5000 или своя). Берётся правило с наибольшим порогом ниже цены; цена не больше нуля не округляется. Применяется к итоговой цене позиции в корзине, итогах, оформлении и «Пересчитать скидки» (скидка позиции = базовая − округлённая, при округлении вверх без скидки может быть отрицательной; доставка и `custom_price` не округляются), к базовой цене и цене со скидкой каталога (`/api/v1` и bxapi) и к ценам в выгрузке в 1С. Админка — «Магазин → Правила округления» (право как у типов цен). Без правил ответы прежние байт в байт.
- **Порядок применения:** подходят активные правила в своих датах, с пересекающейся группой пользователя, без `unsupported`, а купонные — при активном купоне у покупателя; сортировка — `priority` по убыванию, затем `sort`, затем `id`; каждое правило проверяет условия по текущей корзине и считает от цены после предыдущих. Сработавшее правило с `last_discount` останавливает всё дальнейшее, с `last_level_discount` — только остальные правила того же приоритета (правила меньшего приоритета применяются, как в Битриксе). Действие, после которого цена позиции стала бы отрицательной, к ней не применяется (скидка 120 % не делает товар бесплатным); позиции с ценой, заданной вручную (`custom_price`), не участвуют. Деньги округляются до копеек на каждом шаге, как `PriceMaths::roundPrecision`.
- **Корзина** пересчитывается на каждом чтении (снимок bxapi, итоги формы, оформление) с записью `base_price` (до скидок), `discount_price` (скидка на единицу, у наценки — отрицательная) и `price` позиций. В итогах формы «Стоимость товаров» — по базовой цене, «Скидка» — при скидке больше нуля, «Доставка» — со скидкой, «Итого»; при наценке, как в Битриксе, строки «Скидка» нет, а «Итого» — с наценкой.
- **Купоны** (`discount_coupons`): `kind` `basket` (одноразовый на позицию), `order` (одноразовый на заказ), `multi` (многоразовый, лимит `max_use`, 0 — без лимита) — `TYPE` 1/2/4 Битрикса; срок, владелец (`user_id`), описание. Код ищется без учёта регистра (как MySQL Битрикса). bxapi: `POST /api/v1/cart/coupon/add {coupon}` и `POST /api/v1/cart/coupon/remove {coupon}` — ответ снимок корзины; в снимке поле `coupons: [{coupon, status, text}]` (`ENTERED`, `APPLYED`, `BAD`) появляется, только если у покупателя есть купоны. Негодный купон не сохраняется — ошибка 400 (`coupon_not_found`, `coupon_inactive`, `coupon_expired`, `coupon_foreign`, `coupon_used`) с текстами `DiscountCouponsManager` («не найден», «не активен», «дата окончания активности купона раньше текущей», «неверный владелец купона», «купон был применен максимальное число раз»…). Купоны гостя переходят к пользователю при входе.
- **Оформление** фиксирует цены в позициях и отгрузке (`shipments.base_price` — доставка до скидок) и примененные правила в `order_discounts` (название, купон, суммы по позициям и доставке; при удалении правила история остаётся). Одноразовый купон выключается, у многоразового растёт `use_count` (лимит проверяется при оформлении); заказ, проигравший гонку за купон, оформляется без него с сообщением. Отмена заказа купоны не возвращает. Правка заказа в админке скидки не пересчитывает; кнопка «Пересчитать скидки» в карточке заказа применяет текущие правила. Письма и история заказов (`basePrice` позиции) показывают настоящую базовую цену.
- **Каталог:** цена со скидкой — правила, условия которых зависят только от товара и пользователя (без условий корзины и заказа), применённые к одной единице, как `GetOptimalPrice`. Собственный API (`/api/v1/iblocks/...`) отдаёт `price_discount` — цену для гостя, только у записей коллекций с каталогом, которым правило меняет цену; bxapi — `catalogPrice.discountValue`/`discountFormatted` по группам посетителя (`value` остаётся базовой), только при флаге проекта `catalog_price_discount`.
- **1С:** в выгрузке заказа `ЦенаЗаЕдиницу` и `Сумма` — со скидкой, у позиции `Скидки/Скидка` («Скидка на товар», сумма скидки на единицу, как `DISCOUNT_PRICE` у Битрикса, `УчтеноВСумме=true`); скидка доставки — уже в цене доставки. Цены из 1С принимаются как есть.
- **Без правил и купонов** ответы bxapi и собственного API — байт в байт как до скидок.
- **Админка** (право «Скидки», `discounts.manage`), раздел «Скидки»: список правил (активность с переключением, приоритет, сортировка, период, группы, «только по купону», число купонов, предупреждение о неподдерживаемых элементах, удаление); форма правила с конструктором деревьев условий и действий (`static/admin/discount-tree.js`, без библиотек; сервер проверяет классы и ссылки, ошибки — у узла, введённое сохраняется); купоны правила — добавление (пустой код — сгенерированный), генерация пачки до 10 000 (префикс, тип, лимит, срок), выключение, удаление неиспользованных. Даты активности правил и купонов вводятся и показываются по Москве (UTC+3), как при импорте и в условиях движка. В карточке заказа — блок «Скидки» и «Пересчитать скидки» (позиции с ценой, заданной вручную, не меняются; оплаченный и отменённый заказ не пересчитывается). «Корзины покупателей» показывают цены со скидками, как корзина в API.
- **Перенос из Битрикса:** `import-bitrix` переносит `b_sale_discount` (`CONDITIONS`/`ACTIONS` из PHP-serialize в JSON; id инфоблоков, элементов и разделов сохраняются как в Битриксе, коды вариантов справочников заменяются на наши id, группы, платёжки и доставки — по нашим id; неизвестные классы — в `unsupported`), `b_sale_discount_group`, `b_sale_discount_coupon`. Накопительные и подарочные правила (`CondCumulativeGroup`, `CumulativeAction`, `GiftCondGroup`) переносятся и применяются; границы периодов (`Period.ValueStart`/`ValueEnd`, `sum_period_data.discount_sum_order_start`/`_end`) приводятся к unix-секундам: число остаётся числом, дата Битрикса `DD.MM.YYYY[ HH:MI[:SS]]` читается как московская, пустое значение удаляется. `b_catalog_rounding` переносится в `catalog_rounding` (`CATALOG_GROUP_ID` → тип цены с тем же id, `ROUND_TYPE` 1/2/4 → `math`/`up`/`down`); правило с неизвестным типом цены, `ROUND_TYPE` или точностью пропускается с предупреждением, повторный перенос заменяет правила округления целиком (если таблицы `b_catalog_rounding` в источнике нет — правила не трогаются). Старые скидки каталога `b_catalog_discount` и накопительные программы `b_catalog_disc_save_*` не переносятся — предупреждение со списком (`<id «название»>`).
- **Повторный `import-bitrix`** перезаписывает правила и купоны по id Битрикса — правки в админке теряются, у купонов в том числе `use_count` и `active` (использованные у нас одноразовые купоны снова становятся активными).
- **Модуль проекта:** `discount_condition_hook` (`DiscountConditionHook`) — свои классы условий: `class_ids()` и `check(class_id, data, &Context, позиция) -> Option<bool>` (как `OnCondSaleControlBuildList`); такие правила не считаются неподдерживаемыми и проверяются в корзине, заказе и каталоге. `catalog_price_discount` — цена со скидкой в `catalogPrice` bxapi.
- **Не входит:** накопительные программы каталога `b_catalog_disc_save_*`, старые скидки каталога `b_catalog_discount`, перенос исторических заказов, автоматическое добавление подарков в корзину.

## Модули проектов

Настройки и код конкретного сайта (декораторы ответов, группы поиска, формы, проверки форм вроде капчи, характеристики, ширины картинок — аналог `bxapi.*` в `.settings_extra.php` и `init.php`) в репозиторий не входят. Модуль проекта — файл `projects/<имя>.rs` с функцией `pub fn project() -> Project`; он подключается при сборке (`build.rs`) и включается `BXAPI_PROJECT=<имя>`. См. `projects/README.md`.

## Публичный API

Отдаются только коллекции с галочкой «Доступен в API» и только активные записи с наступившей датой публикации. Пути и ключи JSON остаются прежними (`iblocks`, `elements`, `properties`). CORS настраивается через `CORS_ORIGINS`.

| Метод | Описание |
|---|---|
| `GET /api/health` | проверка сервиса и БД |
| `GET /api/v1/iblocks` | список коллекций |
| `GET /api/v1/iblocks/{code}` | коллекция и схема полей |
| `GET /api/v1/iblocks/{code}/elements` | список записей |
| `GET /api/v1/iblocks/{code}/elements/{element_code}` | одна запись |

Параметры списка записей:

- `page`, `per_page` (по умолчанию 20, максимум 100);
- `sort` — `sort`, `name`, `published_at`, `created_at`, `id`; префикс `-` — по убыванию;
- `prop.<код>=<значение>` — фильтр по полю.

```json
{
  "items": [
    {
      "id": 1, "code": "pervaya-novost", "name": "Первая новость", "sort": 500,
      "preview_text": "...", "detail_text": "...",
      "published_at": "2026-09-27T10:30:00Z",
      "properties": { "author": "Иван", "hot": true },
      "created_at": "...", "updated_at": "..."
    }
  ],
  "pagination": { "page": 1, "per_page": 20, "total": 1, "pages": 1 }
}
```

## Права доступа

- **Суперадминистратор** (флаг в карточке пользователя) — полный доступ, права групп не проверяются.
- **Группы** — пользователь может состоять в нескольких, права суммируются:
  - права на разделы: «Вход в админку» (без него остальные не действуют), «Управление коллекциями», «Управление пользователями», «Управление магазином», «Работа с заказами», «Обмен с 1С», «Обмен заказами с 1С», «Скидки»;
  - доступ к каждой коллекции: нет / чтение / изменение. «Управление коллекциями» даёт изменение во всех.
- Группы и членство в них меняет только суперадминистратор; менеджер пользователей не может редактировать суперадминистраторов и выдать кому-либо этот флаг.
- Права пересчитываются на каждый запрос — изменения действуют сразу, без повторного входа.

Коды прав — в `src/access.rs`.

## Безопасность админки

- Пароли — argon2; в БД хранится только sha256 от токена сессии.
- Cookie `HttpOnly`, `SameSite=Lax`, `Secure` при `COOKIE_SECURE=true`.
- Изменяющие запросы принимаются только с того же origin (проверка `Origin`/`Referer` против `Host`). За reverse-proxy он должен передавать исходный `Host`.
