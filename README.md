# CMS на Rust

Headless CMS по мотивам 1С-Битрикс: админ-панель для управления контентом, публичный JSON API для фронтенда и API, совместимое с модулем `mediagroup.bxapi` — фронт, написанный под Битрикс, работает с CMS без правок. Данные переносятся из базы Битрикса одной командой.

**Стек:** Axum 0.8 · PostgreSQL + SQLx 0.9 · MiniJinja (шаблоны админки) · HTMX · argon2.

## Запуск

```bash
docker compose up -d                  # PostgreSQL
cp .env.example .env
cargo run -- create-admin admin       # создать администратора (спросит пароль)
cargo run                             # http://127.0.0.1:3000/admin
```

Миграции применяются автоматически при старте. Отдельно: `cargo run -- migrate`.

Переменные окружения — в `.env.example`.

## Инфоблоки

Инфоблок — настраиваемый тип контента (новости, статьи, товары). У него есть:

- **разделы** — дерево произвольной глубины (код, внешний код, картинка, описание);
- **свойства** — строка, текст, число, да/нет, дата, список (варианты с XML_ID), привязка к элементу (можно ограничить инфоблоком), файл; любое, кроме текста и да/нет, может быть множественным;
- **элементы** — название, код, внешний код, раздел, активность, сортировка, анонс и детальный текст с картинками, дата публикации и значения свойств (JSONB: одиночное — скаляр, множественное — массив; список хранит id варианта, привязка — id элемента, файл — id файла).

Символьный код элемента необязателен (уникален только непустой) и генерируется из названия транслитерацией. HL-блоков отдельно нет: справочник — обычный инфоблок, а свойство-справочник — привязка к элементу (`user_type = directory`, связь по внешнему коду).

Торговый каталог: типы цен, цены, склады, остатки, форматы валют (как модуль `catalog`).

## Перенос из Битрикса

```bash
cms import-bitrix 'mysql://user:pass@host:3306/db' --upload /path/to/site/upload [--replace] [--api-code 14=info]
```

Переносит инфоблоки, свойства, варианты списков, разделы, элементы со значениями свойств (хранение v1 и v2), HL-блоки (как инфоблоки), торговый каталог и пользователей. Id инфоблоков, разделов, элементов, свойств и файлов сохраняются как в Битриксе. Пользователи входят со своими паролями: хеши Битрикса (`$6$…` и старый md5 с солью) проверяются и при входе заменяются на argon2. Повторный запуск с `--replace` заменяет инфоблоки; пользователи обновляются, а не дублируются. `--api-code` задаёт apiCode инфоблоку, у которого API_CODE в базе не заполнен.

## Файлы

`/upload/<путь>` — файлы из `UPLOAD_DIR`; перенесённые лежат по тем же путям, что в Битриксе. `/upload/resize_cache/<ширина>/<путь>` — уменьшенная копия, создаётся при первом запросе. Если задан `UPLOAD_ORIGIN_URL` (старый сайт), отсутствующие файлы докачиваются оттуда при первом обращении — весь `upload` заранее переносить не нужно.

## API в формате bxapi

Под `/api/v1/` — контракт модуля `mediagroup.bxapi` (обёртка `{status, data, errors}`, ключи в camelCase): `iblock/list`, `iblock/info/{apiCode}`, `iblock/{apiCode}/element/list`, `element/{id}`, `element/slug/{slug}`, `section/list` (с `hasElements`), `iblock/{apiCode}/search`, `nav/breadcrumbs`, `nav/legacy-redirect`, `base/csrf/token`, `auth/login|session|logout`.

- `filter` — операторы `=`, `!`, `@`, `!@`, `%`, `<`, `>`, `<=`, `>=`, группы `logic: OR`, спецключи `iblockSectionId`, `sectionSubtreeId`, `sectionCode`, `iblockSection.*`, пути `prop.item.xmlId`, `prop.element.<поле>` (вложенные связи до 3 уровней);
- `select` — поля, свойства и пути через точку, `image`/`imageExt` (+ `imageResize`), `detailPageUrl` (по шаблону URL инфоблока), `sectionName`, `sectionCode`, `catalogPrice`, `catalogQuantity`, `stocks`;
- где документация модуля и поведение Битрикса расходятся (формат пустых значений, порядок по умолчанию), повторяется Битрикс.

## Модули проектов

Настройки и код конкретного сайта (декораторы ответов, группы поиска, характеристики, ширины картинок — аналог `bxapi.*` в `.settings_extra.php` и `init.php`) в репозиторий не входят. Модуль проекта — файл `projects/<имя>.rs` с функцией `pub fn project() -> Project`; он подключается при сборке (`build.rs`) и включается `BXAPI_PROJECT=<имя>`. См. `projects/README.md`.

## Публичный API

Отдаются только инфоблоки с галочкой «Доступен в API» и только активные элементы с наступившей датой публикации. CORS настраивается через `CORS_ORIGINS`.

| Метод | Описание |
|---|---|
| `GET /api/health` | проверка сервиса и БД |
| `GET /api/v1/iblocks` | список инфоблоков |
| `GET /api/v1/iblocks/{code}` | инфоблок и схема свойств |
| `GET /api/v1/iblocks/{code}/elements` | список элементов |
| `GET /api/v1/iblocks/{code}/elements/{element_code}` | один элемент |

Параметры списка элементов:

- `page`, `per_page` (по умолчанию 20, максимум 100);
- `sort` — `sort`, `name`, `published_at`, `created_at`, `id`; префикс `-` — по убыванию;
- `prop.<код>=<значение>` — фильтр по свойству.

```json
{
  "items": [
    {
      "id": 1, "code": "pervaya-novost", "name": "Первая новость", "sort": 500,
      "preview_text": "...", "detail_text": "...",
      "published_at": "2026-09-27T10:30:00Z",
      "properties": { "author": "Иван", "hot": true },
      "created_at": "...", "updated_at": "..."
    }
  ],
  "pagination": { "page": 1, "per_page": 20, "total": 1, "pages": 1 }
}
```

## Структура

```
src/
  main.rs         CLI (serve / migrate / create-admin / import-bitrix), сборка роутера
  config.rs       настройки из окружения
  auth.rs         пользователи, сессии админки
  passwords.rs    проверка паролей (argon2 и хеши Битрикса)
  iblock/         модели, типы свойств, разделы, запросы к БД
  files.rs        загруженные файлы
  uploads.rs      раздача /upload: ресайз, докачка с origin
  api.rs          собственный публичный JSON API
  bxapi/          API в формате mediagroup.bxapi: фильтры, сериализация, разделы,
                  поиск, навигация, вход посетителей; project/ — точки расширения
  import.rs       перенос из базы Битрикса
  admin/          админка: вход, инфоблоки, разделы, элементы, пользователи, группы
build.rs          подключение модулей из projects/
projects/         модули конкретных сайтов (не в репозитории)
templates/admin/  шаблоны MiniJinja
static/admin/     стили админки
migrations/       SQL-миграции
```

## Права доступа

- **Суперадминистратор** (флаг в карточке пользователя) — полный доступ, права групп не проверяются.
- **Группы** — пользователь может состоять в нескольких, права суммируются:
  - права на разделы: «Вход в админку» (без него остальные не действуют), «Управление инфоблоками», «Управление пользователями»;
  - доступ к каждому инфоблоку: нет / чтение / изменение. «Управление инфоблоками» даёт изменение во всех.
- Группы и членство в них меняет только суперадминистратор; менеджер пользователей не может редактировать суперадминистраторов и выдать кому-либо этот флаг.
- Права пересчитываются на каждый запрос — изменения действуют сразу, без повторного входа.

Коды прав — в `src/access.rs`.

## Безопасность админки

- Пароли — argon2; в БД хранится только sha256 от токена сессии.
- Cookie `HttpOnly`, `SameSite=Lax`, `Secure` при `COOKIE_SECURE=true`.
- Изменяющие запросы принимаются только с того же origin (проверка `Origin`/`Referer` против `Host`). За reverse-proxy он должен передавать исходный `Host`.
